## Choose the installation source

Use [GitHub Releases](https://github.com/hxquan-q/open-forge/releases) for released installers. The open-source repository is the source for development builds; do not mix a development data directory with a production profile unless the build explicitly documents that compatibility.

The repository and documentation use **Open Forge**. Desktop defaults to the `distribution` profile, displayed as **Allstr ai** with a localized Chinese name. Builds explicitly configured with `VETTA_BRAND_PROFILE=self` display Open Forge. Package names may vary by profile; use the exact filenames from the release. Both profiles share the `OpenForge` executable name and the default `~/.openforge` data root, so switching brands does not isolate data. Branding is independent of lite/full cloud-service mode; check the release notes for the selected build.

Windows x64 releases provide three formats. The Inno `.exe` installer is recommended for most users and participates in in-app updates. Use `.msi` for standard Windows Installer deployment, or extract `.zip` and run `OpenForge.exe` without installing. MSI and ZIP are supplemental downloads; in-app updates still use the Inno installer.

Linux releases currently target x64 and provide AppImage, DEB, and RPM packages. Use AppImage without installing, DEB on Debian/Ubuntu, or RPM on Fedora/RHEL-family distributions:

```bash
# Run in a download directory containing only the intended packages

# Debian / Ubuntu
sudo apt install ./*.deb

# Fedora / RHEL family; direct-download RPMs are not GPG-signed yet
sudo dnf install --nogpgcheck ./*.rpm

# AppImage
APPIMAGE="./<exact-downloaded-filename>.AppImage" # Replace with the actual filename
chmod +x "$APPIMAGE"
"$APPIMAGE"
```

The DEB and RPM files are currently distributed directly over HTTPS rather than through an APT or DNF repository. After installation, the app updater continues using the same package format.

Before upgrading, record the current Open Forge version, operating system, architecture, and the location of any local projects you need to keep.

## Cloud-service mode

The lite build omits accounts, subscriptions, and the hosted model catalog; full builds can include Open Forge Serv integration selected at build time. Both can use GitHub ability sources. This is separate from the brand profile and cannot be switched after installation without a different build.

See [configuration and data paths](/reference/configuration-paths/) for development roots, environment overrides, and legacy-data migration.

## Update safely

1. Finish or stop active tasks and wait for background work to reach a known state.
2. Export diagnostics if you are investigating an issue.
3. Install the new version over the existing application when the installer supports in-place updates.
4. Reopen Open Forge and verify sign-in, model configuration, one existing project, and one small read-only task.

## Move to a new device

Projects and credentials have different recovery requirements. Copy project files through your normal secure backup process. Re-authenticate on the new device and configure credentials again instead of copying browser cookies or OAuth state.

<Callout title="Do not copy secrets blindly" type="warn">
  Never upload or share API keys, OAuth cookies, pairing QR codes, webhook URLs, or an unredacted diagnostic bundle. Check the [security and data boundaries](/reference/security-and-data/) before collecting logs.
</Callout>

## If an update breaks a workflow

Capture the version and the last successful step, reproduce the issue with the smallest project and model, and inspect the execution history. If a downgrade is necessary, preserve the new diagnostic evidence first and verify that local session data remains readable by the older build.
