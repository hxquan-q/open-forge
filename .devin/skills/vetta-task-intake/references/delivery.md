# 工程完成、产品接受与反馈回流

## 证据分层

| 层次 | Agent 要记录的事实 | 不能替代的内容 |
|---|---|---|
| 工程验证 | 实际版本/提交、覆盖行为、命令/结果、未运行项 | CI 绿灯不证明遗漏需求或真实模型质量 |
| 技术评审 | 对实际 diff/合同的发现、修复、剩余风险；注明独立评审或自审 | 实现 Agent 总结不是独立评审 |
| 集成 | Task branch/commit、集成结果、集成后验证 | Worker 绿灯不证明组合正确 |
| 人工功能验收 | 用户对功能行为、交互、AI 产物的明确反馈 | 不要求用户默认逐行审核代码；沉默不算接受 |
| 发布 | 明确授权及实际发布状态 | 已提交/已推开发候选不等于稳定发布 |

沿用 [Project 状态](../../../../project/CONVENTIONS.md)，不新增平行状态机。功能任务工程通过后可进入 verifying；用户尚未验收或拒绝时不能自行设 done。integration_status 独立记录 pending/reviewing/integrated/rejected。内部任务人工验收不适用时说明理由及既定完成标准，不伪造“用户已确认”。历史 done 记录不批量重解释。

## 功能验收包

用户不应为验收学习内部架构。只交付足以判断结果的内容：

- 本次解决的用户问题与不做项。
- 可用版本/提交、入口与必要前置条件；尚未运行或不可访问时明确说明。
- 代表性操作步骤/AI 任务输入及预期行为、最终产物。
- 明确的不通过表现、已知限制与需要用户决定的取舍。
- 简短工程证据摘要及未验证边界；详细日志留在 Task/Verification，不灌给用户。

UI/Provider 实机流程未获授权时提供步骤与自动化证据，不自行启动实例、调用付费模型或声称人工测试完成。高风险技术问题必须在用户能理解的影响层面暴露，功能演示成功不能抹掉数据、安全或兼容风险。

## 验收不通过

1. 由 Agent 区分需求理解偏差、实现缺陷、环境问题和模型质量问题；先复用已有证据，只有拿不到必要输入才问用户。
2. 将反馈变为 Given/When/Then 或带合格标准的评估案例，关联原 Task；真实缺陷按 Bug 规范记录，新增范围另行拆 Task。
3. 回到相应实施/诊断路线，补适合自动化的回归证据，避免用户重复发现同一问题。
4. 重做受影响流程与集成验证，交付修正后的验收包；用户确认后关闭，发布仍需独立授权。
