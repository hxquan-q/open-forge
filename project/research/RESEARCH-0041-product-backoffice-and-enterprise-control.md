# 产品运营后台、个人与企业授权及企业管控设计调研

当前范围更新：用户最新明确第一期为个人注册登录与管理、个人Web中心、Skill/MCP市场、官网介绍/文档/下载及产品依赖镜像，支付不考虑。当前执行建议以 [PLAN-0023 r4](../plans/PLAN-0023-product-platform-backoffice.md) 与 [REQ-0029](../requirements/REQ-0029-product-backoffice-and-licensing.md) 为准；本研究保留此前企业/商务/私有化研究作为历史与后续输入，不能继续当作第一期范围。

## 问题与范围

用户希望产品可以公开发布，并支持版本发布、插件/MCP/技能市场、企业管控。用户已选择“个人公开版 + 企业团队版”，随后明确顺序：**先建设自己运营产品的后台，优先登录注册、个人与企业授权，再建设企业管控，市场能力逐步接入。** 用户进一步确认尚未创建或开发自己的后台，fork 时隐藏了上游相关客户端；本轮需要先给方案。方案已记录到 [REQ-0029](../requirements/REQ-0029-product-backoffice-and-licensing.md) 与 [PLAN-0023](../plans/PLAN-0023-product-platform-backoffice.md)，均为 draft。

本轮交付为调研与建议设计，未修改运行时代码、创建生产服务、运行真实客户端、调用付费模型、上传制品或发布。下文“建议”“目标模型”“阶段”均非已实现功能，不构成现有决策的替换或实施授权。

建议先形成一个完整闭环：运营人员在后台创建套餐并给客户授权 → 客户注册登录 → 个人获得权益，或企业分配席位 → Desktop 拉取有效权益 → 到期、移除席位或撤销后在明确时限内失效 → 全部管理变更可审计。

## 当前结论：先运营后台，再企业控制台

### 1. 产品表面与权限边界

建议共用一个服务端领域模型，提供以下入口，按阶段开放，而不是先建多套互不相通的系统。

| 入口 | 使用者 | 负责什么 | 优先级 |
|---|---|---|---|
| 产品运营后台 | 自己公司的运营、销售、支持、发布人员 | 用户、企业客户、套餐、授权、版本、市场运营、管理审计 | 第一优先 |
| 用户中心 | 个人用户与企业成员 | 注册登录、账号恢复、个人权益、设备/会话、加入企业、切换使用空间 | 与第一期配套 |
| 企业控制台 | 客户企业的 owner/admin/billing 等角色 | 成员邀请与席位、账单查看；随后加入策略、批准目录、SSO/SCIM、审计导出 | 第一期开最小成员/席位面，深管控后续 |
| 开发者中心 | 官方内容团队、后续第三方发布者 | 发布者身份、能力提交、版本、权限变化、审核反馈、撤回 | 后置；首期可由运营代办 |
| 官网及公开市场 | 访客与客户 | 产品说明、下载、版本说明、帮助、能力发现 | 与后台共用已批准的发布记录 |

运营后台角色与客户企业角色必须分开。企业管理员不能给自己增加商业权益或扩大购买席位；支持人员也不应默认获得全部客户会话内容或发布权限。平台操作客户授权要留主体、理由、前后差异及关联销售/支持凭据。

### 2. 三种“授权”不能混成一个会员等级

| 授权领域 | 回答的问题 | 建议权威来源 |
|---|---|---|
| 管理权限 RBAC | 谁能创建套餐、给客户授权、发布版本、管理某企业成员？ | 平台管理员角色、组织成员角色、服务端资源归属 |
| 商业权益 Entitlement | 某个人/企业买到了哪些功能、多少席位/额度、到什么时候？ | 有效授权、套餐功能、席位分配及服务端用量账本 |
| 执行权限与企业 Policy | 该次工具调用能否读文件、执行命令、访问某 MCP？ | 宿主真实能力边界、组织强制策略、项目约束及用户批准 |

不能用 `isVip`、`isEnterprise` 或“管理员”一个字段承担三件事。付费不能绕过敏感工具审批；企业 admin 也不是平台 superadmin。用于灰度的 feature flag 不能单独授予商业权限。

### 3. 第一版运营后台的信息架构

建议第一版菜单压到八组，每组都有对应用户流程和审计，不先追求大而全。

| 菜单 | 首期可用功能 | 暂缓 |
|---|---|---|
| 总览 | 有效用户、授权客户/即将到期、已分配席位、待处理事项 | 缺少事件口径时的复杂经营大屏 |
| 用户 | 查询、状态、验证情况、关联企业、会话撤销、发起账号恢复流程 | 直接查看密码、替用户登录、默认读取本地文件/会话 |
| 企业客户 | 创建客户、指定 owner、成员邀请、席位使用情况 | 复杂部门树、跨企业代理运营 |
| 产品与套餐 | 定义可售功能、席位/设备上限、期限、配额规则和套餐快照版本 | 动态计价表达式和开放脚本执行 |
| 授权中心 | 个人/企业试用、正式授权、续期、停用/撤销、变更记录 | 一开始就做多渠道自动支付、开发者结算 |
| 版本中心 | 记录候选版本、绑定可信构建制品、平台架构、说明、测试结果、发布状态 | 网页输入 shell 命令构建、随意覆盖同版本包 |
| 审计与操作记录 | 授权/角色/发布等变更查询、筛选和导出、受控保留 | 默认记录员工全部提示词、代码和文件 |
| 基础设置 | 登录/注册策略、通知模板、受保护的服务连接、管理角色 | 明文显示长期 secret、通过业务设置开放任意宿主能力 |

市场条目管理可在后续加入同一后台，不先做独立的三套管理站。

## 登录注册与个人/企业授权设计

### 4. 身份、组织和使用空间

建议 `User` 是全局身份；`Organization` 是企业客户；`Membership` 记录某用户在某企业的状态和角色；邀请与加入需有独立状态。一个用户可以有个人权益，同时加入多个企业；企业资源请求必须带明确有效的组织上下文并由服务端核实成员关系。

用户中心呈现“个人空间 / 企业 A / 企业 B”。同一人切换空间时切换计费主体、权益、企业策略与资源范围。企业 owner 离职、转移 owner、移除成员、邀请过期/重复接受需要明确定义，不能删账号代替退出企业。

云端组织空间不等于 Desktop 本地“项目”，构建用 `tenants.json` 的打包档位也不等于 SaaS 企业租户。不要重用这些现有词或 id 代替客户隔离。

初期选择一种可运营的注册入口；建议邮箱注册/验证/恢复作为默认候选，第三方登录或手机号按客户约束确定，不假设用户已有身份供应商。登录、验证码/邮件、找回流程必须防滥用和账号枚举。后台管理员要求强化认证；客户无需在第一期就接入完整 SAML/SCIM。

Desktop 建议沿现有主进程 OAuth 入口演进，核查授权码/PKCE、state、一次性回调与 token 轮换合同，避免登录页把长期 token 放进可传播 URL。Web 会话与 Desktop token 的存储合同分别处理；账号禁用/会话撤销需要服务端执行，UI 登出只是其中一个动作。[S14]

### 5. 套餐、授权、席位、用量分别建模

建议先支持“后台人工开通 + 客户自助登录使用”，待流程稳定再接支付，避免支付集成反过来定义产品所有权限。

| 对象 | 最低职责 |
|---|---|
| Product / Plan / Feature | 产品、套餐修订、稳定功能标识、套餐对应的功能与限制；已生效合同保留购买时快照 |
| License / Grant | 授权主体为个人或企业；记录来源、状态、生效/到期、功能/额度/席位快照、撤销原因 |
| SeatAssignment | 企业购买的席位分配给成员；与 `Membership` 分开，加入企业不自动占用或获得付费席位 |
| EntitlementSnapshot | 某主体在某使用上下文实际可用的功能和限制，带 revision 和有效期；是授权结果，不是价格表副本 |
| DeviceActivation / Session | 某次设备安装激活及登录会话；设备数量与席位数量不同，不等同硬件指纹 |
| UsageLedger | 云服务端权威计量、预留/扣减/结算/释放及去重；BYOK 本地统计与云收费账本分开 |

个人授权绑定个人；企业授权绑定组织，席位再分配给成员。不要给每个员工发一份长期个人高级会员来模拟企业购买，否则离职回收、续费主体、企业停用都会混乱。

授权建议状态为待生效、试用/有效、到期、暂停、撤销，并区分后台申请、审批与实际生效。首期手工开通/续期同样使用幂等请求和事务，保留授权来源及操作人。到期提醒、续费和升降级不能破坏既有客户的合同快照。

企业开通 20 席位时，后台记录可用席位上限，企业管理员分配；第 21 个并发分配必须被服务端事务拒绝，不能靠前端计数。取消成员后按确定规则回收席位和组织会话，不自动删除其个人账号与个人数据。

如需兑换码，只把它作为领取某项 Grant 的一次性/限次入口：服务端保存不可逆摘要及使用记录，避免让可分享的永久激活码变成授权事实源。

如需云模型额度，必须按请求标识去重并约定失败/取消/部分响应的计量规则；不能用客户端上报的 token 数直接扣费。第一期未提供云代付时不必先建设完整计费引擎。

### 6. 在线校验、离线使用与撤销

云付费 API 由服务端校验主体、权益、额度，不能信任客户端套餐缓存。Desktop 可缓存短期签名的授权结果，包含主体、上下文、产品、revision、有效期及必要设备绑定；公钥验证只证明签发来源，不证明客户端没有被用户修改。

离线宽限期、最大撤销延迟、个人与企业差异应作为产品参数明确。无需首期支持永久离线许可；如果商业合同要求离线内网部署，单独设计签名文件、续签、设备迁移、时间回退和撤销限制。

必须承认：**长期离线可用与即时远程撤销不能同时保证。** 在线客户可主动失效，离线客户端只能在预定租约/连接条件恢复后重新判定。撤销授权不得静默删除用户本地文件或已产出结果。

开源本地客户端的商业限制不能提供“用户绝对无法绕过”的保证。更强的企业约束依赖受管设备、网络出口控制或服务端执行；后台管理按钮本身无法阻止用户在系统其他进程使用自己的工具。

### 7. 第一期必须走通的连续流程

1. **个人开通**：注册并验证身份 → 登录 → 运营授予试用/正式权益 → Desktop 获取有效结果 → 到期/续期/撤销 → 状态按合同同步，临时网络失败不误判为账号被撤销。
2. **企业开通**：运营创建企业客户与企业授权 → owner 接受邀请 → 分配有限席位 → 员工登录并选择企业空间 → 取消席位后企业权益失效，个人空间仍可访问。
3. **账号恢复**：丢失登录凭据或设备 → 通过受控恢复流程 → 撤销旧会话/设备 → 新设备重新激活，记录操作者与依据。
4. **支持纠错**：误开/误撤授权 → 根据审计记录执行新的更正操作 → 保留原记录，禁止删除历史伪装未发生。
5. **越权拒绝**：用户替换组织 id、重复接受邀请、重复开通、并发占用最后席位 → 服务端保持正确归属与一致结果。

## 版本发布：后台编排，CI 构建，客户端兼容

### 8. 构建成功、允许发布、用户已安装是不同状态

建议分为 `ReleaseCandidate`、不可变 `BuildArtifact`、分发规则 `Rollout` 和客户端安装结果，避免用一个“已发布”布尔值含混表示。

目标流程：固定 commit/版本 → CI 测试与构建 → 平台签名/公证及制品校验 → 后台登记候选与可信证据 → 审批 → 内测/小范围推广 → 扩大范围 → 稳定发布；发现问题后暂停推广、标记问题版本并发布修复候选。

后台管理的是批准的固定流水线、候选记录和分发范围，不允许运营人员提交任意命令让 CI 执行。CI 回调需校验真实构建身份及 commit/制品关联，处理重试和重复事件。签名私钥留在受保护发布环境；条件支持时采用 OIDC/短期凭据，不能把长期 CI token 打包到客户端。[S13]

产品版本、构建 id、App/API/配置兼容版本分别记录。保留 `apps/desktop/package.json#version` 及现有发布规则，后台不能先维护一个与仓库不一致的手填版本事实源。

每个制品固定产品/版本/平台/架构/摘要，禁止覆盖同版本的不同字节；渠道指针和推广范围可以变更但必须留 revision 与审计。默认下载页、更新 feed 和发布说明读取同一批准的发布事实，避免各自手填。

个人早期可继续现有 stable/test；未来增加 beta 或企业验证环应作为迁移设计，不直接改现有更新路径。企业可以延迟更新和锁定已支持版本，需定义安全支持窗口、过期提醒与紧急补丁策略。[S10]

灰度用稳定分组条件，例如客户端安装标识或组织 cohort，避免每次随机重新抽样。大文件走对象存储/CDN，API 负责鉴权、选择和短时下载凭据；企业私有制品不能仅靠猜不到的公开 URL 隔离。

暂停推广只阻止更多用户升级，不会恢复已经安装的客户端。优先采用更高版本修复；实际回退必须先验证数据格式、插件兼容和平台安装机制。Windows 版本目录能力不代表所有平台和数据都能安全降级。[S11]

第一期先打通版本登记、可信制品和受控上线；自动灰度、崩溃门限自动暂停等按可靠事件采集成熟度追加，不制造没有数据支撑的“成功率”。长期需要签名元数据、过期/防回放、撤销和密钥轮换；完整 TUF 引入应独立评估，不宣称已有依赖版本支持最新文档中的所有能力。[S12]

## 企业管控：在授权基础上逐步增加

### 9. 先成员/席位，再可执行策略

企业第一期具备组织隔离、owner/admin/member、邀请、席位、离职回收、管理审计；在此基础上增加模型与 BYOK 限制、批准能力目录、更新策略、SSO/SCIM，最后按客户需求增加数据驻留、私有分发及强隔离执行。

有效执行能力应受平台硬边界、组织强制限制、项目更严格限制与用户批准共同约束；下层不能通过普通设置覆盖上层拒绝。用户对某次敏感操作仍可拒绝；商业付费不等于替用户同意执行。[S4]

策略至少覆盖安装、更新、启用/加载、导入、手工配置、开发模式和实际调用。批准一个市场来源不等于批准来源中所有版本；仅隐藏市场条目会遗漏本地 Skill、旁加载插件、手工 MCP 和命令行入口。[S5]

每份策略带 schemaVersion、revision、作用域、生效/到期和可验证来源。客户端回报收到/应用的 revision、版本和失败原因；后台区分未连接、不支持、应用失败、已生效。签名或回执不能代替 OS 级设备可信证明。[S1]

组织切换、在途工具调用、后台自动化、断线、策略过期必须有合同：新调用按新策略判定；已开始的调用依据可取消性和副作用风险处理，不能把所有调用一律强杀或继续。个人空间不能借用企业 token，企业审批也不能被切回个人模式隐式沿用。

策略失效后，高风险新企业操作拒绝；本地数据查看/导出与已授权离线工作依事先定义的合同处理。不能把控制服务临时断线解释为删除或冻结所有个人数据。

管理员审计默认保存操作主体、组织、动作、资源 id、策略/授权 revision、结果及脱敏差异，不收集 token 或完整工具参数。提示词/文件内容留存、运行遥测和 SIEM 导出另设用途、可见范围及保留规则。[S3]

## 市场：统一目录与运营，保留不同执行模型

### 10. 市场后台在账号和授权稳定之后接入

共用发布者、namespace、详情、可见范围、审核、投诉、版本、组织批准、商业授权与撤回，沿用现有 skill/scene/plugin/mcp/bundle 类型，必要时对前台归类，不删除现有消费者支持的类型。

| 类型 | 分发内容 | 额外合同 |
|---|---|---|
| Plugin | `.vettapkg` 等固定制品、宿主 API 范围与权限 | 宿主 UI/代码/工具生命周期；可信代码与隔离能力明确标示 |
| Skill / Scene | `SKILL.md` 及脚本、参考资料、资源 | 安全解包、内容来源、依赖与工具需求；Skill 文本不成为管理授权指令 |
| 本地 MCP | 固定版本包/镜像/二进制和运行配置 | 安装与启动授权、运行环境、依赖、凭据、进程回收 |
| 远程 MCP | 已核验服务 URL、连接描述及 OAuth 元数据 | 平台账号与第三方服务 token 分离、工具范围、连接状态和服务变更 |

MCP Registry 适合上游发现，不应直接当产品的私有目录、运行服务或安全背书；导入后仍需产品审核和企业批准。远程服务可在 URL 不变时改变实现或工具列表，因此不能套用本地不可变包的全部保证。[S6][S7]

首期仅官方或受邀发布者；发布流程建议为草稿 → 提交 → 自动检查 → 人工审查 → 批准指定版本/摘要/权限 → 上架。扩大权限、外部地址或依赖时重新判定。签名、身份验证、扫描和隔离分别展示，避免统一“安全认证”徽章。[S8][S9]

公开、未列出、组织私有、企业批准可见是不同维度；私有列表、详情和下载都校验权限。弃用、停止新安装、撤回恶意版本、停用已安装版本也要分开。离线设备的紧急撤回有不可消除的延迟，需与授权租约和更新策略共同设计。

迁移可先让新后台输出现有 Schema v3 目录及固定制品，保留 GitHub 源作为兼容入口；具备新的可信来源验证后再扩客户端协议。不要发布后台管理 token、企业 secret 或内部 MCP 凭据到公开市场快照。

## 技术形态、阶段与取舍

### 11. 独立新建模块化后台，复用客户端接线

建议独立新建私有后台，业务域为 Identity、Customer/Organization、Authorization、Release、Catalog、Audit；先在一个后端中保持清晰模块边界。可按现有团队栈采用 TypeScript 与 React，具体框架待实施规格选择。登录中心/成熟身份组件承担标准身份协议，产品服务自己拥有组织、客户合同、席位及商业权益，不把身份提供商当整个业务数据库。

事务型数据库承载客户/席位/授权，已有数据库可满足时继续用；制品使用对象存储/CDN；可靠后台作业处理通知、过期、发布回调、扫描。先复用已有队列/任务机制，出现吞吐和独立隔离需求后才引入 Redis、新队列或拆服务。

管理 API 与客户 API 的认证与权限分离，每个租户请求由服务端注入/验证归属；异步任务、下载地址、缓存、对象路径和日志同样携带正确作用域。RLS 等机制可作纵深措施，不能代替应用鉴权。

第一期不建议同时自建身份协议、支付系统、任意代码沙箱、MCP 托管集群和微服务平台。新建方案可将 PostgreSQL 作为事务库候选，具体 API/身份/UI 框架、SSO 采购或自托管、支付渠道和地区方案留到实施规格；不能把未取得的上游私有后台当默认依赖。

### 12. 建议实施顺序与验收门

| 阶段 | 交付范围 | 通过什么证明可进入下一阶段 |
|---|---|---|
| A：新后台规格与接入合同 | 以已核实的客户端和上游分仓事实建立 API/身份/授权合同，选择新后台组件与独立仓库边界 | 有可复用客户端与需新建服务端清单，不依历史 ADR 假定现有后台 |
| B：产品后台与授权闭环 | 后台人员登录、用户、企业客户、套餐、人工个人/企业授权、邀请/席位、账号恢复、审计；用户中心与 Desktop 对接 | 正常开通/续期、个人与企业切换、最后席位并发、账号禁用/撤销、网络波动与跨租户拒绝流程可验证 |
| C：版本运营闭环 | 候选/制品登记、固定 CI 流程、审核上线、下载/更新事实统一；再加入灰度 | 未批准候选不进入更新范围；错误摘要/签名被拒；重复回调无重复上线；暂停后无新增升级，已安装用户有修复路线 |
| D：企业治理 | 批准目录、模型/工具/出网/版本策略、策略回执；按客户顺序接 SSO/SCIM | 实际运行入口拒绝禁止项；成员离职回收；不支持客户端被识别；断线/在途任务处理符合合同 |
| E：市场运营 | 官方能力目录、发布与审查、组织私有内容、撤回；之后开放第三方中心和支付 | 同版本不可覆盖；权限扩大重审；私有资源全链路鉴权；撤回/停用有客户端证据 |

阶段 B 的最小企业成员/席位界面不代表已经实施阶段 D 的完整管控；企业身份集成若为签约前提，可将对应 SSO 薄切片前移，而无需先建全套市场。

是否接自动支付/订单、离线许可或私有化部署以真实客户和销售流程触发，不阻塞先用人工授权售卖。未检查服务端和团队产能前，不给日历工期与金额承诺。

### 13. 被否决或后置的方案

- **先做全量市场再补后台账号/授权**：与用户最新优先级相反；上架、购买、企业可见性都会缺少共同身份。
- **个人版与企业版各一套用户和授权库**：同一客户迁移与多企业身份难以保持一致；改为共享身份和上下文隔离。
- **给企业员工批量发个人高级会员**：无法可靠表达购买主体、席位回收与企业策略；使用组织授权和席位分配。
- **拿本地缓存或一枚永久激活码做全部授权**：无法提供可靠撤销和云端费用控制；采用服务端事实及明确离线租约。
- **只有后台权限/市场 UI 控制**：实际加载、手工配置和执行入口可绕开；治理需落实到宿主和服务端边界。
- **后台直接覆盖安装包/市场版本**：来源追溯、客户端缓存和恢复路径都失去稳定身份；固定制品，变更推广指针。
- **一开始全面微服务化、部署 MCP Gateway、实现任意第三方插件沙箱**：尚无规模和客户证据；先按模块治理并保持真实信任边界。

## 失效条件与置信度

- 对本仓客户端现有接线、市场类型、插件摘要校验和仓库边界：置信度高，已回读当前源码；运行环境和远端服务可用性未验证。
- 对用户没有自有后台：用户已直接确认；对上游独立 `vetta-serv` 的实现和可取得性：未知，不作为交付前提。
- 对建议的信息架构、模块边界与顺序：为本次目标下的工程判断，需随实际后台、客户类型、部署地区和团队资源调整。
- 若首批企业必须完全内网/永久离线、强制 DLP/隔离执行，或要求本地全部功能不可绕过收费，需先重定信任模型与交付范围。
