# Code 模式审计问题分阶段修复

## 背景与目标

TASK-0407 交付的总体检测报告（工作区 `code-mode-audit-2026-10-30.md`）确认了 F01–F10、G01、M01 等问题。用户授权按「修复难度升序、优先级降序」逐问题分阶段修复；本计划承载该批次的目标、切片顺序与验证合同。

范围（用户 2026-10-30 确认）：

- 修复 F01–F04、F06、F08–F10、G01、M01；
- 落实报告 §11.3 决策：LLM 行为热追踪收敛为 code 模式独有（生产端按会话档位过滤写入，消费端非 coding 挂载点不跟随；团队会话天生 coding 档，维持现状）；
- F10 产品决策：新建 code 会话恢复四个默认页签及固定顺序，创建后的手动调整保留。

明确不做：F05 终端跨项目隔离（早期演示已接受的限制）、F07 运行中流式输出（可选能力缺口，后续按需）、M02 OOM 根因调查（独立诊断线）、报告 §5.3 中与本批无关的环境/测试维护失败（远程退出码、市场超时、资源夹具、rg PATH、profile 快照）。

## 当前事实

- 基线 `98f7de9e6`（本地 main，chenxvhua 检出）。TASK-0339/0392 的浏览器合同与页签跟随修复候选仍在工作树未提交，本批必须保留且不得夹带。
- 报告第四节各问题已经独立代码复核（报告 §11.1），机制与源码一致；本批不重跑诊断探针作前置，以各切片自建红→绿回归为准。
- 热追踪现状：生产端 `useSessionEventController` / `useTeamChatModel` 无档位闸门；消费端含 work 会话手动打开的活动面板等多个挂载点（报告 §11.2）。

## 候选方案与取舍

- 主检出串行逐片（采纳）：单会话执行，热点文件（ActivityPanel、会话事件泵）与既有未提交候选重叠，拆 worktree 并行会放大合并风险。
- 一次性大批提交（否决）：违背一提交一事与逐片可回滚；每片独立验证后再提交。
- 按报告第八节三批分组（否决）：用户明确要求难度升序/优先级降序综合排序；依赖关系（F10 依赖 F01/F02，F03 依赖活动身份）优先于严格难度序。

## 不做什么

- 不动 TASK-0339/0392 已验证候选的语义（本批在其上叠加，不重写）；
- 不删除或放宽 §5.3 既有失败测试的断言换绿；
- 不启动 `verify:ui:*`、不连真实 Provider、不操作用户运行中的 Desktop；
- 不做远程 Git 操作（push/fetch 等由用户手动执行）、不发布。

## 验证与回滚

- 每片定向测试（仓库 Node runner）+ 影响面；行为变化逐片写 v0.1.4 fragment。
- 回滚单位为单片提交；热追踪收敛（§11.3）生产端与消费端过滤必须同批落地，避免「写了但看不到」中间态。
- 已提交的本批切片可按提交回退；不回退他人/他任务的提交。

## 升级信号
