本机只读预检 `wsl.exe --list --verbose` / `--status` 均 exit 1，返回未安装 WSL；尚不能记录当前会话的 WSL2 已就绪。若用户所指为其他环境，部署时从该环境核验，不自动安装、不更改宿主设置。

## Requirement Run（Phase 1，TASK-0334）

用户要求的能力是“给出一个大需求，Agent 拆解后持续推进，直到该需求的全部流程完成”，而不是只把现有 `loop` 队列跑空。现有 `queue`/`loop` 是有界 Task 队列执行器：每次领取一个 ready Task，`done + integrated` 才解锁依赖，空队列、依赖等待、路径冲突或连续停滞即停止；它不知道 REQ 条款是否全部被覆盖，也没有需求级完成报告。planner/triage/lessons 目前是建议入口，不会生成已授权 Task。

Phase 1 只补“需求级覆盖与工程完成判定”，不改 Task/租约/依赖语义：

- 输入为 REQ 条款 R1..Rn、PLAN 与 Task DAG，以及 Agent 拆解时生成的机器可读 coverage manifest；每个条款必须绑定至少一个本 REQ/PLAN 内的 Task 和可核对的 repo-relative 证据路径。
- 串行复用现有 `cycle` 执行本 manifest 内的 eligible Task，仍走实现→异家族评审→验证→（显式 L2 时）集成；不领取 manifest 外的 Task，不并行写入，不自动创建 ready Task。
- 完成判定分三层：`engineering-complete` 只表示所有条款的 Task 均已集成且证据路径存在；`humanAcceptance` 仍为 pending，除非对应 Task 已是 done 且用户接受；发布始终为 `not-authorized`。
- 停止原因至少覆盖 `engineering-complete`、`coverage-gap`、`blocked`、`stalled`、`needs-human`、`failed`、`limit`、`paused`、`cancelled`，并保留未覆盖条款、未执行 Task 和下一步。
- 不在 Phase 1 把 `verifying` 改成可解锁依赖；依赖 `verifying` 前驱的任务按 `needs-human` 停下。若以后要引入“工程完成即可依赖”，另建治理 Task 与迁移合同。

TASK-0334 是本阶段的实现合同，已按上述边界实施：`scripts/agents/requirement-run.mjs`、coverage/report schema、`requirement-check`/`requirement-run` CLI 与测试；定向 19 例、agents 116 例、记录检查 31 例与完整 check 通过。Task 保持 verifying，独立评审、真实需求运行与人工验收仍待执行。Phase 2 的自主发现/分诊、Phase 3 的有界并行实现、Phase 4 的发布/遥测分别另立 Task，均不以本阶段记录视为已授权。

## 候选方案与取舍

采用仓库协议、确定性执行与可替换模型进程；不把多厂商 CLI、Git notes 或提示词当作安全边界。运行记录采用单写者、原子持久化和租约 fencing，Task 继续是语义合同。跨机器共享存储以后只能在明确的存储合同上扩展，不能把普通本地锁称为分布式锁。

3. TASK-0330：完成分项 readiness；区分本地软件、模型执行与完整发布条件，每项保留证据、原因和未执行项。延期项目不能被标为通过，也不能妨碍无关的本地代码测试。
4. 补齐角色到工作流的消费路径：planner 建议经合同校验形成 Task 草稿，triage 进入可复现调查，lessons 消费真实复盘材料形成候选；外部内容和模型输出不能直接生成已授权的 ready Task 或强制规则。TASK-0326 的角色入口不等于这些路径已实现。

6. 完成文档与本地验证后按 concern 原子提交；不能为了收尾夹带现有 UI 草稿或他人 temp 文件。代码阶段跑最低充分行为测试、impact 和完整 check；本轮计划更新本身不表示这些代码已完成。

第 4、5 项是从实际源码发现的接线工作，不能假定已有命令会自动完成；实施前按现有 Project 路由补相应 Task，避免扩大 TASK-0328–0330 的责任边界。

### B. 在 WSL2 验证真实开发闭环

先核实实际 WSL2 发行版、资源、Linux 文件系统仓库副本及 Bun/Node/Git 兼容性；不复用 Windows 的 node_modules，不直接把当前带未提交改动的工作区当作已提交基线。控制器状态、日志和工作副本都用专用目录，不读取真实 Desktop 状态。

真实模型启动前，固定可调用的实现者和异家族评审者、实际模型身份及必要授权；验证 Worker 的 OS 权限/凭据隔离和整个进程树回收。模型可执行文件存在或 CLI 已登录不能替代以上条件。当前这些条件未满足，level=0 和 disabled 保持。

满足后先单任务、单实现者运行，沿公开入口完成领取→实现→异家族评审→本地验证→合并候选重新评审和验证→按现行权限集成。测试/UI/远端检查缺失时停在对应待验收点，普通代码任务不得借延期越过必要检查。以后才增加连续多 Task 和定时调度。

故障验收必须包含：评审拒绝、候选改变、目标分支前进、执行超时、控制器重启、租约过期/旧 Worker 回包、资源清理不确定。预期是留下可诊断证据、拒绝重复集成、未知清理暂停；恢复不能清空状态或伪造成功。

### C. 用户指定的延期验收

账号额度恢复后，由当前最终候选重新取得三平台 CI 与 packaged 检查，不能复用旧提交的绿色结果。真实 UI 验收在明确授权后运行受影响用户流程、交互/布局断言、三主题×明暗和独立视觉检查；失败进入修复与相应回归。UI 可用性不是 CI 额度的同一事实，本次二者均依用户决定延期。

这段延期阻止完整跨平台/UI 验收和依赖这些证据的发布，不阻止 A 段的软件编写。额度恢复前不循环触发失败 CI，不修改预算，也不安排未经请求的定时提醒。

### D. 完整 L4 的最后验收

部署并验证独立控制面的签名/制品/发布/清理服务与真实遥测；同一最终提交的检查、独立评审、制品摘要及可信回执必须一致。发布响应丢失先对账、不能盲重试；崩溃超过阈值或遥测缺失时确实暂停，恢复需要健康观察与显式恢复动作。

现行策略灰度为 1%→10%→50%→100%，每阶段 48 小时，最低样本 500，遥测新鲜度 15 分钟。样本不足继续等待，不造流量或静默降低门槛；如需调整，另走策略治理。

稳定分支、tag、Release、上传和部署继续按仓库既有明确授权执行。若未来希望普通 patch/minor 发布在限定范围内自动进行，须先明确范围并更新权限合同，不能把本次“看看怎么实现 L4”解释为已授权。七类人工闸门、未知分类与目标冲突仍保留。

完整 L4 的验收包必须同时含 A 的实现与软件测试、B 的真实模型/隔离/故障证据、C 的最终候选跨平台/UI 结果，以及 D 的真实发布/监控结果。没有固定“一个月自动达标”的时间承诺。
