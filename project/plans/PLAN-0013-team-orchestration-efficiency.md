# 团队会话编排效率：消除主控轮询空转与协作摩擦

## 背景与目标

「开发团队」实测数据中台任务（`--E--demo--` 会话组，01:45–02:30）暴露三类系统性低效：

1. 主控回合 45min 中 ~89% 时间用于 `team_wait_tasks` 轮询（38 次等待、34 次 timeout），
   已有的 `triggerTurn` 完成唤醒路径完全未被使用；
2. 成员会话广告了不可用的 `browser_tab`（`no_browser_session`），被迫绕行自建服务；
3. 质检深度不分级，「简单页面」任务走完独立审计+修复全回路（~47% 时长）。

目标：不改动任务持久化/重试预算/通知投递等已验证正确的合同前提下，把「等待」从模型轮询
改为让出回合等唤醒，把不可见阶段改为可见进度，把不可声明的能力改为显式边界。

## 当前事实

- 唤醒机制已存在且实测工作：`agent-team.task-completed.v1` 通知持久化进 journal，发起者空闲时
  `triggerTurn` 续跑（`team-task-notification.ts`）；回合忙时通知顺延至回合结束投递。
- 缺口在策略层：master.md 与 `team_wait_tasks` 描述鼓励就地观察，无「分派后结束回合」引导；
  timeout 返回全量 workItem JSON（实测 ~7-8KB/次，38 次累计 ~300KB 回灌）。
- 主控 input 503,860 tokens 高于任何干活成员，等待是主控成本主项；全任务 $0.376、31M
  cacheRead（缓存 miss 型供应商上成本会数倍放大）。
- 上游 218 提交领先；`887017560` 已做「队长优先+模型请求事件驱动等待提示」（启动侧），
  不覆盖轮询回合；上游已把 `team_delegate_task` 描述缩短（self-contained 要求改由委派合同承载，
  `ea5a5da50`）。
- 同赛道共识：Pi rolebox 图引擎「结束回合、引擎唤醒」已生产化；Codex #15723 社区方案=
  「runtime 拥有唤醒、通知持久去重、回合忙时顺延合并」——与我们的机制方向一致；
  Codex #24951（wait 阻塞 7.5h）反证我们有界 wait（60s）是对的设计。

## 候选方案与取舍

| 方案 | 收益 | 代价 | 取舍 |
|---|---|---|---|
| A 提示词+载荷瘦身（让出引导 + timeout 返回精简状态） | 立即消除大半空转与回灌 | 小；合同测试 | **采纳为阶段 1** |
| B 运行时自动挂起回合（协调器检测「仅剩等待中工作」时挂起发起者，通知唤醒续跑） | 不依赖模型自觉 | 回合生命周期改动大，与 262d88b38 重构过的准入路径交互复杂 | 暂不立项，等阶段 1 实测残差 |
| C 质检分级字段进委派合同 | 审计回路可控 | 级次主观、需产品判断 | 挂起，待第二次「简单任务质检过重」实测证据（ISSUE-0027 决策触发条件） |
| D 阶段化进度可见 | 不省时间但显著改善体感 | UI 实现 | **采纳为阶段 2** |
| E 等上游合并 | 零投入 | 覆盖度不明 | 拒绝——上游只覆盖启动侧，轮询回合问题持续 |

## 阶段

- **阶段 1（低成本半步）**：TASK-0122 让出引导+timeout 瘦身；TASK-0123 成员 `browser_tab`
  不可用声明。两者互不依赖、可并行不同 worktree。
- **阶段 2（体验）**：TASK-0124 团队会话阶段化进度展示（委派/执行/审计/收尾），draft 待设计细化；
  TASK-0126 预算可视化（成员/会话级 token·回合·时长只读投影，ISSUE-0028 候选 C 最小步）
  搭其投影面，serial 随其后。
- **阶段 3（验证）**：TASK-0125 rebase 上游后同任务复跑量化对比（等待调用数、主控 input、
  总时长、$成本），产出 Verification 记录；数据决定 B/C 是否立项。

## 不做什么

- 不改 workItem 持久化模型、任务重试预算（`maxAutomaticRetries`）、通知 journal 语义——
  这些已被实测证明正确；
- 不做运行时强制挂起（方案 B 本期不立）；
- 不做会话级预算/熔断（新缺口已登记为 ISSUE-0028：会话无回合/墙钟/token 上限与可路由
  blocked 态，收敛全靠主控自觉；触发条件见其「决策触发条件」）；
- 不动审计员角色本身与团队组成；
- 不为成员会话引入可见 WebView（ISSUE-0026 推荐 B 的 headless 渲染属另一独立工具评估）。

## 验证与回滚

- 阶段 1 验证：合同测试断言 timeout 载荷形状与让出提示；提示词 diff 评审；真实会话复跑抽样。
- 阶段 3 为整体验证闸：同一数据中台任务复跑，对比基线（38 waits / 503,860 主控 input /
  44.9min / $0.376）。
- 回滚：阶段 1 全部为提示词与工具输出合同变更，单独 commit 可独立 revert；无持久化格式变化。

## 升级信号

- 阶段 1 落地后复测仍 >30% 主控调用为等待 → 升级方案 B 立项；
- 出现第二次质检回路占比 >40% 的实测 → ISSUE-0027 方案 A（质检级别字段）立项；
- 出现第二次「会话 >30min 未收敛」或成员返工回路 >3 轮 → ISSUE-0028 方案 A/B 立项；
- 上游再引入团队编排新机制（如事件驱动 wait 本体） → 重估方案 B 必要性。

## 需要的 ADR

- 不需要。全部为策略/合同层调整与既有机制的使用方式修正，不改变架构边界；若阶段 2 引入
  新的 UI→主进程阶段事件协议，届时按 ADR 判据单独立项。
