# 团队任务质检深度无分级：「简单页面」任务走完独立审计+修复全回路

## 背景

用户任务是「创建一个简单数据中台页面」。团队实际执行了完整四段流水线：
抽取（12.5min）→ 构建（12.4min）→ **独立审计（14.7min）→ 修复（6.4min）**。
审计+修复回路占全程约 47% 的时长与约 $0.18 的成本（审计员 $0.078 + 修复段开发员部分）。

审计质量极高：直读源 xlsx 逐格复算、幂等实验、否定用例、发现源表两处真实异常并回写修复了
页脚口径文案。价值真实存在——问题在于**深度是否应按任务复杂度/用户意图分级**，以及谁来定级。

## 已知事实

- 审计并非用户要求，是主控依据 master.md「Inspect every returned result and accept it only when it
  meets the goal」自行编排的；内置团队固定含审计员角色，也会引导主控走审计回路。
- 审计员产出的 `audit-report-data-platform.md`（14KB）对「简单页面」目标而言超出预期，
  但其发现的 I-1（页脚口径对互调1/2不成立）是真实缺陷，若省掉审计该缺陷会带上线。
- Claude Code 对同类问题的答案是「按工作形态选编排」：subagents / agent teams / dynamic
  workflows 分级，且明示「teams 显著增加 token 消耗，串行/高依赖任务用单会话更优」；
  Codex 则把 spawn 决策交给显式请求并默认收敛为单回合整合。
- 当前主控没有任何「任务规模→质检深度」的显式刻度，只有模型自由心证。
- 行业里有三种可参照的分级形态：
  - **GitHub HydraFusion**（2026-09 研究预览）：按任务路由 Single / Cascade / Critique
    三档——简单任务单模型直达、中等任务低成本模型先行+质量检查不过再升级、高价值任务
    才走「A 生成 B 独立评审 C 修订」；官方离线评测质量 +4.9pt、成本 −67%。核心结论是
    「把昂贵推理集中到真正需要的任务上」，不是模型越多越好。
  - **multica-best-practices**：门禁阶梯（G0 需求收敛人工确认 → G1/G2/G2.5/G3 → G4
    人工验收），且**角色按范围条件路由可缺失**（Tester 无后端时跳过、轻量版 squad 只有
    单层门禁）；关键约束「所有门禁由 Leader 用独立 verification skill 复跑，不采信成员
    自述」「产物修改后下游门禁立即失效」。
  - **pi-task / pi-goal-x**：确定性任务管线把质检做成 verify/enforce **门**而非默认角色；
    goal 规划配独立 completion auditor——审计作为「按需挂的门」而非「常驻成员」。
  - **pi-subagents（tintinweb）`SubagentWorkflow`**：`agent()` 的 `gate: "npm test"` 参数
    **用真实命令验证子代理产出而非再派一个模型**——把分级光谱从「有无审计员」二选一
    打开成四档：无门 → **确定性命令门**（跑测试/构建/渲染检查，成本近零且结果可复核）
    → 模型评审 → 全量审计。本次「简单页面」任务若有一道 `gate`（起本地渲染+取 DOM
    断言 KPI 值）就足以挡住大部分交付缺陷，不必动用 14.7min 独立审计员。
- 对「返工回路」的防护参照：multica 写死「返工超 2 次 / 证据矛盾 → 升级人类」；
  我们没有这条规则（见 ISSUE-0028）。

## 未决问题

1. 质检深度分级的触发维度是什么：用户明示（「简单」/「生产级」）、主控判断、还是任务书字段？
2. 「简单」任务的合理下限是什么——构建者自测？成员抽查？还是保留审计但收敛范围（如只验 KPI
   数值不验幂等性）？
3. 分级如果不做，是否至少在用户侧明示「正在审计」（当前只有统一的工作动画，45min 无任何阶段
   提示——与 ISSUE-0025 的进度可见性问题叠加）。
4. 审计回路对纯展示/原型类任务的边际价值如何用数据衡量（本次发现 1 项重要文案缺陷，算不算
   值得 21min）？

## 候选方案

| 方案 | 收益 | 代价 | 风险 |
|---|---|---|---|
| A 任务书/委派合同加「质检级别」字段（self-check/spot/full-audit） | 分级显性化，主控有据可依 | 合同字段设计+模型遵守度 | 级次划分主观 |
| B 默认收敛：非用户明示生产级任务，审计员只做「交付物存在性+冒烟」抽查 | 直接省掉大半审计时长 | 可能漏掉 I-1 类缺陷 | 质量水位下降需接受 |
| C 保持现状 | 质量最大化 | 每次任务 40min+ 与成本 | 用户对「简单任务很慢」的体感持续 |
| D 进度可见性兜底：审计阶段向用户显示阶段名与预计范围 | 不省时间但显著改善体感 | UI 阶段化展示实现 | 与 ISSUE-0025 方案耦合 |

## 推荐

短期 D（先让审计存在对用户可见、可解释），中期 A（委派合同引入质检级别，默认按任务书推断）。
不建议 B 的硬收敛——本次审计抓到的 I-1 说明「简单任务」也可能藏着真缺陷。

## 决策触发条件

- 出现第二次「简单任务耗时 >30min 且大半在质检回路」的实测数据时，A 应立为 Task。
- 若产品方向确认「团队模式默认走完整质检」，则把耗时预期写进团队模式的引导文案。
