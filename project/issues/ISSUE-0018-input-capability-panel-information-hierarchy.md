# 对话输入区能力建议面板信息层级待优化

## 背景

用户指出，对话输入区中的 Skills、MCP、计划模式、图像生成和制作插件入口仍需要优化。截图显示输入框上方展开了一整块能力/Skill 建议面板，面板覆盖部分正在阅读的消息；条目说明被截断或弱化，面板底部还并列放置计划模式、图像生成和制作插件操作。用户难以快速辨认这些入口分别是什么、当前能否使用，以及它们与 Skill/MCP 列表的关系。

用户目标：在输入区快速找到并使用相关能力，同时不遮挡当前对话，也不需要理解内部 Skill、Connector、Operation 等实现分类。

## 已知事实

- `apps/desktop/src/renderer/domains/conversation/components/command-panel/CommandPanelView.tsx:21` 将命令面板描述为 InputBar 的展开形态，并以绝对定位向上生长，目的是不推动消息列表；`:78` 设置面板叠层位置，`:85` 将内容高度限制为 `min(320px, 40vh)`。
- 同文件 `:123` 将 ConnectorGrid 与 SkillList 放在同一滚动区，`:144` 将其他 actions 固定在滚动区底部。
- `apps/desktop/src/renderer/domains/conversation/components/command-panel/types.ts:38` 将底部操作抽象为统一的 action 项；当前实现的 Skill、连接器、上下文操作与底部动作具有不同交互角色。
- 截图证明面板展开时会与会话内容发生视觉重叠，部分长描述被截断；截图没有证明具体哪些操作被禁用或是否由运行中状态导致淡化。
- Desktop 的 UI 文案和组件边界须遵循 `apps/desktop/docs/user-language-ui.md`、`apps/desktop/docs/composable-ui-components.md`；现有“不推动消息列表”的交互不变量需要保留或显式重新评估。

## 未决问题

1. 用户最需要优先触达的是“能力入口”（Skill/MCP/计划/图像/制作插件），还是当前输入触发的 Skill/命令搜索结果？
2. 能力入口是否应在面板关闭时仍作为输入框工具栏常驻，或继续只在面板展开时显示？
3. 生成进行中时各入口哪些仍可交互，哪些必须禁用；禁用原因是否需要清楚解释？
4. 对小窗口、长列表和长描述，面板高度、分组、搜索及描述展示应采用何种响应策略？

## 候选方案

| 方案 | 收益 | 代价 | 风险 |
|---|---|---|---|
| A. 只做视觉收敛：压缩行高、改善文本截断和选中/禁用态，维持当前内容分组与展开方式 | 变更面小，不改输入心智模型 | 当前列表与能力入口的概念混杂仍存在 | 只缓解密度问题，用户仍不易发现或区分能力 |
| B. 按用户目标重组：把“选择/搜索 Skill 与连接能力”和“计划、图像、制作插件”等工具动作分区；控制面板占用面积并明确可用状态 | 角色清楚，长内容更易扫描，入口与搜索结果不再竞争层级 | 需要核实各入口的常用性、依赖状态和运行中行为 | 若把低频动作提升为常驻入口，会增加工具栏噪声；布局调整可能影响既有快捷键和焦点合同 |

## 推荐

采用 B 的信息架构方向，但先以真实常用路径核实入口优先级，再决定哪些操作常驻、哪些保留在面板内。保留面板不推动消息列表的既有约束；优先改善分组、清晰度、长文本呈现和运行中可用状态，不通过扩大面板解决信息层级问题。

## 决策触发条件

确认代表性用户任务中 Skills/MCP/计划/图像/制作插件的优先级和生成期间的交互规则后，形成可验收的面板布局合同，再拆实现 Task。截图中的重叠属于当前展开形态下的展示现象；只有进一步证明它阻断阅读或输入时，才单独登记为回归 Bug。

## 后续 Task

- UI 方向确认后拆出“能力面板信息层级与交互优化”Task；需覆盖真实组件渲染、键盘/焦点导航、长描述/小窗口及生成中禁用状态，并验证展开面板不推动消息列表。
