# Open Forge Desktop 首发 SemVer 基线

## 背景

用户已确认 Desktop 使用 Open Forge 独立 SemVer，并将 upstream commit 作为单独来源元数据；首发具体版本号和 Preview/Stable 定位尚未决定。当前 Desktop manifest 仍继承 `0.5.59`。

## 已知事实

- Release Notes、Desktop tag scope 和 Desktop 发行包版本读取 `apps/desktop/package.json#version`。
- 当前 release-notes parser 只接受纯 `X.Y.Z`，没有 SemVer prerelease 后缀合同。
- Desktop release workflow 已有 test/stable channel 配置；实际首发产品成熟度未冻结。
- 当前没有授权执行 version bump、创建 tag 或发布。

## 决策结果（2026-09-23，用户四轮决策确认）

- **成熟度与受众**：首发为面向早期用户的 **Preview**，小范围公开分发；§4(b) 声明策略、实机安装验收与品牌全量验证完成前不做 Stable 承诺。
- **首发版本号**：`0.1.0`。origin 无 tag/Release、无已分发 Open Forge 构建，不存在版本降级问题；`0.5.60` 外观像 Vetta 序列延续，与独立 SemVer 初衷相悖。
- **分发形态**：GitHub Release 源码 + 安装包。首发平台 **Windows + Linux**；macOS 因签名/公证 secrets 未确认而从首发发布路径排除，凭据配好后补发（workflow 需支持 macOS leg 条件化）。
- **Preview 语义**：走 default/stable 渠道建正式 GitHub Release，并用 `--prerelease` 标记为 Pre-release；不用 test 渠道（它不建 Release，外部无法下载）。
- **上游基线记录**：Release Notes 正文末尾固定一行 `Upstream baseline: upstream/dev@<sha>`，`prepare` 时以 `git merge-base upstream/dev HEAD` 自动写入。
- **执行方式**：`prepare` 可由 Agent 代跑产出 diff 供审查；`publish --confirm-publish` 由用户亲自执行（远端不可逆副作用留在权利人手里）。
- **prerelease 后缀**：不引入 `X.Y.Z-beta.N` 版本号；Preview 语义由 GitHub Release 的 prerelease 标记与说明正文表达，版本解析器保持纯 `X.Y.Z` 不变。

## 未决问题（已裁决，存档）

首个 Open Forge 外部分发版本属于早期 Preview 还是稳定产品承诺？初始版本号和是否采用 prerelease 后缀应如何确定，且如何验证更新器的版本比较与旧 Vetta 来源隔离？

## 候选方案

| 方案 | 收益 | 代价 | 风险 |
|---|---|---|---|
| `0.1.0` Preview | 清楚表示 Open Forge 新产品线尚未稳定 | 需要确认从任何测试构建到首发的升级路径 | 若产品已承诺稳定，版本号可能低估成熟度 |
| `0.5.60` 数字序列 | 使用现有三段 SemVer 工具，无需解析 prerelease | 外观上继续沿用上游版本历史 | 用户可能误认为是 Vetta 版本延续 |
| `1.0.0` Stable | 明确承诺首个正式稳定发行 | 需有与 1.0 稳定承诺匹配的验收和支持准备 | 当前品牌/合规/身份工作未完成，过早承诺稳定 |
| `0.5.x-beta.N` | 能显式标注预览构建 | 需要升级 parser、tag、Release Notes 和 updater 合同 | 多处版本比较逻辑可能不接受 prerelease |

## 推荐

在成熟度未确认前不改 Desktop `version`。若第一批对象是早期测试用户，优先评估 `0.1.0`；只有产品负责人确认稳定承诺后才选 `1.0.0`。暂不引入 prerelease suffix，除非确认现有 updater 与发布流水线将共同支持它。

## 决策触发条件

- 产品负责人确认首发受众和 Preview/Stable 承诺；
- 查询 Open Forge 仓库现有 tag、Release 与测试更新路径；
- 版本解析、tag scope、Release Notes 和 update feed 的合同测试通过。

### 新增

- **会话可以「升级为任务」，右侧活动面板多出「任务」页**：把当前会话升级为任务后，这个请求就有了独立的生命周期——发送消息时任务自动进入执行，回合结束停在「等待审阅」，你可以通过、要求返工或拒绝；返工后再发一条消息任务自动继续。执行中可以随时暂停或取消，暂停的任务不会被回合终态误收尾。任务产出的文件以「产出物」形式列在任务页里，文件被移动或删除时会标出「文件缺失」，但任务记录和产物清单仍然完整。整个任务状态随会话事件日志持久化：中途关闭应用再打开，任务进度、绑定回合和产出物引用都会原样恢复，不依赖界面是否曾开着。升级入口在活动面板的任务页空态里，属于显式操作——普通对话不会被自动转成任务，代价是想要持久化的长任务需要先点一下「升级为任务」。
- **项目可以统一收紧 Agent 的工具面**：项目根 `.vetta/policies/tools.json` 声明本仓库不允许 Agent 使用的工具（含 `mcp__` 前缀的 MCP 工具名），对团队所有成员、所有会话生效——用户显式选择的工具、Work 布局的默认工具集都会被这份名单再过滤；名单把某个工具面清空时该会话就真的没有这些工具。策略只能收紧不能放宽，格式不对时创建会话会明确报错而不是悄悄忽略。同名工具（如插件与内置重名）先到先得，后注册的不会静默顶掉先来的。
- **项目级约定随 Git 共享，本机状态绝不入库***：项目根下的 `.vetta/` 目录（技能、策略、任务模板、Agent 说明）现在有了正式的清单格式——`.vetta/project.json` 声明版本与各子目录开关，签入仓库后团队成员克隆即按同一约定装载；没有清单的老项目保持原行为不受影响。本机专属状态（项目信任等）放在 `.vetta-local/`，应用首次打开项目时会自动把它加进 `.gitignore`（已手写过忽略规则的文件不会被动）；清单版本比应用新时明确报错并提示升级，而不是猜着读。详见仓库内 `docs/vetta-project-conventions.md`。
- **文件批量整理先预览后执行***：在 Work 会话里让 Agent 整理一批文件（分类重命名、归档移动）时，它会先把完整的变更清单——每个文件从哪里移到哪里、为什么——列在确认卡片上，你点「执行整理」才会真正动磁盘；拒绝或超时则一个文件都不改。执行按文件逐个落地并汇报结果：目标文件已存在时跳过保护、来源已不在时明确说明、中途停止时剩余文件标记取消——重试只处理没成功的项，已经改过名的绝不会再来一遍。所有路径被限制在当前项目目录内，越出项目边界的移动直接拒绝。
- **高风险工具执行前需要你逐次批准***：Agent 要跑 shell 命令、联网类 MCP 或插件工具这类高风险动作时，现在会先弹出审批卡片，写清工具名、风险等级、参数摘要和将影响的文件路径，你选择「允许本次」它才会继续执行。可以在卡片上勾选「本项目内以后不再询问该工具」——这个信任只保存在项目本机的 `.vetta-local/` 里，随时可撤销，且**最高风险（L4）与未识别的工具无论何时都逐次确认**，信任也盖不掉；反过来，任何审批都只对卡片上展示的那次动作生效，不会升级成对整个工具的长期授权。谁批准过什么、何时批准的，都会作为会话事实记进事件日志，重启后可查。风险只能被参数和目标往上提、不能被模型往下压；无法判定风险的能力一律按最高风险拦下。命令行（CLI）等未接入审批界面的宿主不受影响，行为与原先一致。
- **可以把远程主机上的目录当作项目打开**（沿用上游条目，fork 侧差异：远端 helper 目录为 `~/.cache/openforge/helper/`）：设置里新增「SSH 主机」，可手动添加或从 `~/.ssh/config` 导入已有别名，并逐台测试连接；随后在「添加项目」里选择「从远程主机添加」，浏览远端目录并登记为项目。
- **会话页顶栏新增「编程 / 工作」模式切换（预览骨架）**：在会话、新会话和项目页顶部可以按项目切换工作区形态——「编程」保持现有界面；「工作」把右侧面板换成按「计划 / 来源资料 / 产物 / 审阅与导出」分区的工作面板。目前各分区是占位骨架，任务执行数据尚未接入（属后续迭代）；切换按项目记住，不打断进行中的会话，也不影响 Agent Team 等自带面板的界面。在「工作」布局下新建的会话，默认不携带 shell 命令类工具（读写文件、文档转换等照常可用），需要时可以在会话配置里显式打开——这只影响默认开箱集合，不是权限限制；已存在的会话不受影响。

### 改进

- **桌面端品牌由统一层呈现**：中文和英文界面中的 Vetta 产品称呼现在显示为 Open Forge，无需改写上游 locale 文件；凭据运行名、技术兼容标识、appId、协议 scheme、更新行为和既有制品命名保持不变。
- **超长会话更省内存、事件落盘不再越写越慢**：此前会话每追加一条事件都要把整份会话文件完整读回并重新解析，会话越长、每写一条的内存峰值和耗时越高。现在活跃会话在主进程内复用已解析的状态，追加只处理新事件；任何外部改动都会被检测并自动回退到完整读取，恢复与冲突提示行为不变。
- **单条超长回复期间内存有界**：模型单次输出特别长（例如流式生成一整个大文件）时，界面重连后只回放这条回复最近一段的原始流，而不是无上限地保留全部流事件；完整内容仍以落盘记录为准，回复正常结束时展示不受影响。
- **渲染端会话统计不再无限累积**：随会话切换保留的逐轮统计缓存现在最多记住最近 128 个会话；计划模式状态回落到未开启时也会清掉对应投影，长时间反复开关会话不再缓慢吃内存。
- **子代理快照不再跨会话无限累积**：用过的子代理（含其完整输出文本）此前会按会话一直留在内存里，即使早已切走也不释放；现在最多保留最近 128 个会话的快照，当前会话与最近使用的不受影响。
- **工具结果里的图片和音频不再整份驻留内存**：会话里模型用工具产出的截图、音频等媒体，此前以 base64 形式整个留在消息数据里，一个有几十张图的会话轻松吃掉数百 MB，滚出屏幕也只是看不见、内存照占。现在消息里只保存一条引用，图片进入视野时才从主进程按需加载，离开视野后由系统的图片缓存自动回收；会话文件不受影响，历史会话重新打开时同样生效。代价是滚动浏览大量工具图片时每张首次进入视野会有一次本地加载（有永久缓存，同图不重复取）。
- **插件和扩展工具的超大结果不再无上限进入会话**：插件、扩展工具返回的结果（含完整返回值与卡片数据）此前不经任何大小策略，一次几十 MB 的返回会原样写进会话文件并常驻内存。现在它们与内置工具走同一条统一策略：超过 50KB 的文本截断并附完整结果文件引用，超大返回值随完整结果落盘、界面上的插件卡片照常展示，图片沿用与 MCP 相同的媒体准入（单项 8MB、单次 24MB 内保持显示）。正常大小的结果完全不变。代价：超大结果的会话导出 HTML 会以摘要形式渲染该条工具结果（完整内容仍在 artifact 文件中）。
- **IM 消息里的 Agent 子进程有了内存上限**：每个 IM 会话拉起的 Agent 子进程此前没有内存约束，极端长对话可把单个子进程吃到数 GB 才罢休；现在每个子进程的堆上限为 2GB，超限时该会话的 Agent 以明确的内存错误退出并自动重启恢复，而不是无声地把整机内存吃满。代价是单条 IM 会话的上下文如果真的超过 2GB（极罕见），该会话会反复重启直至停止自动恢复。
- **编辑器打开过的文件不再永久占用内存**：在应用内预览、编辑过的大文件，此前会把完整内容（含编辑草稿的一份副本）一直留在内存里，浏览的文件越多积累越多，即使早已关闭预览也不释放。现在关闭文件预览时会释放已同步的内容，缓存最多保留 32 个文件；未保存的草稿不受任何影响（关闭编辑器、超出上限都绝不回收），关掉应用前的「有未保存更改」保护也保持不变。被回收的文件重新打开时走一次正常的磁盘加载，与首次打开一致。
- **快捷面板窗口改为首次唤出时才创建**：此前应用启动后就会在后台预先创建快捷面板的隐藏窗口及其渲染进程，即使你从不用双击功能键唤出它，这部分内存也一直占着。现在窗口在第一次唤出时才创建、之后常驻复用。代价是首次双击唤出会晚零点几秒出现（正在创建窗口和页面），第二次起与原先完全一致；首唤瞬间「最近会话」列表会短暂显示为加载中，属预期。
- **异常庞大的 MCP 响应会快速失败**：MCP 服务器返回超过 64 MiB 的单条 HTTP 响应（或 stdio 单条消息超过 16 MiB）时，现在立即以协议错误失败并断开，而不是把整个响应读进内存后再处理；正常大小的结果（包括媒体类）不受影响。
- **代码高亮缓存有了内存上限**：对话里模型反复输出大文件、大段 JSON 时，这些代码块的高亮结果会整个留在缓存里（此前只限制条数，不限制体积），长时间使用后可累积数百 MB。现在高亮缓存增加了约 10MB 的总量上限，超出时最旧的内容先让位；被挤出的代码块滚动回视野时会重新高亮一次，界面上已在看的代码块不受影响。
- **Agent Team 的空闲会话不再永久驻留内存**：打开过的团队会话此前会在主进程里一直保留全部成员与协调会话的运行时状态，即使早已切走、任务全部结束也不释放，用得越多常驻内存越高。现在空闲团队会话只保留最近 2 个热窗口，更旧的完整释放——会话文件与历史不受影响，重新打开时自动从磁盘恢复（与重启后的恢复走同一链路）。正在运行、有未完成工作（包括等待外部资源恢复的任务）、页面仍开着的会话永不释放。顺带修复：成员投递回执此前只增不减并随会话状态落盘，积累过长时会让整个团队会话无法加载；现在回执按最近 256 条封顶，旧数据在读取时自动收敛，不再触发加载失败。
- **桌面宠物 vivi 首次安装后默认不再自动弹出**：第一次打开应用时桌面上不会再冒出一个置顶的宠物窗口。该功能随后在本版本整体暂时下线（设置入口同步隐藏），之前已经开过或关过宠物的用户保持原来的选择不变。
- **Provider 失败诊断不再丢失服务商与模型身份**：此前「Provider 一个事件都没返回就断开」和 DeepSeek/兼容网关上「请求还没发出就被取消」这两类失败，错误详情里没有携带是哪个服务商、哪个模型出的问题，日志与团队任务归因时只能看到一个孤零零的错误码。现在所有 Provider 适配器在这两条路径上都保留身份字段，与其余失败路径一致。
- **点「停止」或关闭会话后，界面不再有机会一直停在「正在停止」**：此前取消会话依赖底层工作（Provider 响应、工具、上下文压缩）自己响应取消信号，如果它不响应，会话会无限等待，发送新消息只报「会话正忙」。现在取消有宽限时间（默认 10 秒）：到点仍未收尾时，会话进入明确的「需要恢复」终态，停止/关闭/切换会话的等待都会按时返回，排队中没发出去的消息会保留而不是被悄悄丢掉，之后可以通过恢复流程把未完成的回合作废并重开会话。
- **使用统计里的「上下文压缩」计数不再恒为 0**：此前压缩次数只在逐会话的监控订阅里累计，而 Agent Team 成员、协调会话等路径发生的压缩根本没有订阅，只进了日志、没进汇总，导致主日志里明明有多次压缩（含失败），统计里 started/succeeded/failed 全是 0。现在压缩计数改在 Runtime 宿主级观察口统一累计，与日志同一采集点——交互、批量、定时、团队等所有会话路径的压缩都会计入，重启后数字照常恢复。其余统计项口径不变。
- **Agent Team 成员任务失败不再被误标为「已完成」**：此前成员回合遇到 Provider 协议错误这类终态失败时，协调器只凭「回合结束」事件收尾，把失败成员记成了完成，父任务拿到的也是假成功。现在成员的失败会带着错误原因进入终态并照常通知父级；成员被宿主中止时则记为「已中断」。同时停止/关闭 Agent Team 任务增加了收尾宽限：成员不配合中止时，协调器在宽限期后强制释放并发额度并继续关闭会话，不再无限等待一个失控的成员。
