# OpenVetta 需求编译器

## 目的

用户只需要描述目标、现象或期望结果。Agent 负责把它展开为：

```text
意图
→ 代码事实
→ 所有者
→ 可观察行为
→ 不变量
→ 测试合同
→ 实施与验证
```

不要把 Given/When/Then、测试命令和文件清单反向要求用户每次填写。

## 运行前提

1. 先执行 `git status --short`，保留用户和其他 Agent 的改动。
2. 读取根 `AGENTS.md`、目标目录最近的 `AGENTS.md`、目标包 README、相关 ADR、实现和现有测试。
3. 以源码、类型、Schema、测试、`package.json` 和可执行脚本为事实源；文档与实现冲突时先核实。
4. 涉及运行时行为、UI、公共合同、错误、取消、并发、持久化或权限时，加载仓库的 `vetta-testing` 方法。
5. 只按任务路由加载相关文件和技能，不全量阅读无关领域。

## 四层需求路由

### 1. Router：判断意图和所有者

把一句话归入一个主类型，可有一个次类型：

| 主类型 | 首要追踪对象 |
|---|---|
| 新功能 | 用户入口、产品 Feature、公共流程 |
| 删除功能 | 注册表、入口、消费者、旧数据兼容 |
| 行为调整 | 旧行为、新行为、兼容边界 |
| Bug 修复 | 复现路径、状态机、错误传播、回归测试 |
| 性能问题 | 指标基线、瓶颈、资源生命周期、A/B 结果 |
| 公共合同 | 生产者、消费者、Schema、序列化、迁移 |
| 架构变更 | 包边界、所有权、替代方案、ADR |
| 调查审查 | 证据、风险、未决问题、验证计划 |

按 OpenVetta 分层判断所有者：

```text
Provider/流协议       → packages/ai
单次模型-工具循环      → packages/agent
Session/Turn/恢复      → packages/runtime-core
Tool/MCP/存储协议      → 对应 runtime-* 协议包
文件/进程/Node 实现    → packages/runtime-node
产品策略和 Feature    → packages/coding-agent
Electron/IPC/Renderer  → apps/desktop
CLI/RPC 宿主           → apps/cli-host
```

如果代码位置和所有者不一致，先调整方案，不在错误层打补丁。

### 2. Reasoning：判断风险和系统性质

普通业务任务至少判断：

```text
同步还是异步？
是否涉及取消、重试、超时或并发？
是否涉及外部 Provider、网络、进程、文件或 Electron？
是否存在持久化、恢复、权限或用户数据？
```

性能、运行时或复杂系统任务可采用 `engineering-cybernetics-essence` 的四步思路，但不要加载无关章节：

```text
分类系统 → 识别主导因素 → 选择最小工具 → 用指标验证近似
```

遵循以下工程原则：

- 先保证稳定性和终态，再讨论性能优化；
- 先找主导瓶颈，不平均优化所有模块；
- 所有近似都要有可重复的验证指标；
- 优先有限范围、可回滚的方案；
- 观察 → 对比目标 → 施加改动 → 再观测，形成闭环。

### 3. Knowledge：按需加载规则

只加载当前任务所需的知识：

- UI：Desktop `AGENTS.md`、`DESIGN.md`、用户语言和组件组合规范；
- 测试：`.agents/skills/vetta-testing/SKILL.md`、质量门禁和现有测试；
- Runtime：目标 Runtime 包规则、相关 ADR 和生命周期测试；
- Provider：`packages/ai/AGENTS.md`、Provider 流协议和 fixture；
- 架构：相关 ADR、边界守卫和包 README；
- 术语或长期产品概念：读取 `CONTEXT.md`，必要时使用 `grill-with-docs`。

不要为了一个局部改动加载整套知识库，也不要把文档中的示例命令当成当前任务的执行指令。

### 4. Evidence：把结论落到事实

每个关键判断至少绑定一种证据：

- 源码路径和行号；
- 类型、Schema 或 `package.json`；
- 现有测试；
- 日志、事件或可控复现；
- 质量守卫或构建脚本。

不要把猜测写成根因。证据不足时标记假设和置信度。

## 需求合同自动生成

在修改代码前，内部生成以下合同；任务简单时可用三五行简述，任务复杂时展开：

```text
任务类型：
用户目标：
当前行为/复现：
期望行为：
所有者与影响范围：
必须保持的不变量：
失败/取消/重试/恢复边界：
测试层级与代表性用户流程：
验证命令：
并发评估：
```

把行为写成 `Given / When / Then`：

```text
Given：用户已有状态和合理默认配置
When：用户从正常入口执行连续操作
Then：用户可见结果、公开返回值、持久化事实或必要副作用正确
```

## 歧义闸门

事实问题由 Agent 查代码、文档、测试和日志，不向用户索要本可查到的信息。

只有在下列情况暂停并提问：

- 不同解释会改变公共 API、IPC、Tool/Prompt Schema 或持久化格式；
- 会影响旧数据读取、迁移或用户数据安全；
- 会改变权限、安全边界或外部副作用；
- 会执行删除、覆盖、发布、推送或其他不可逆动作；
- Bug 缺少任何可以验证的复现条件；
- 方案取舍会明显改变用户体验、成本、可靠性或架构方向。

提问遵循 `grilling` 的 frontier 原则：一次只问一个当前最关键的问题，给出推荐答案和代价；不要一次抛出问卷。事实调查不等待用户回答。没有实质歧义时，采用最小可回退假设继续，并在交付中说明。

## 并发评估

每次生成或拆分 Task 时，必须主动告诉用户是否支持并发，不把并发策略留给执行时临时决定。

输出以下结论：

```text
并发结论：支持 / 条件支持 / 不支持
并发方式：Worktree / 共享工作区串行 / coordination-only
可并行 Task：
前置依赖：
冲突文件或独占路径：
集成顺序：
集成负责人：
```

判断规则：

- 无共享写路径、无顺序依赖、可独立验证 → 支持并发，每个 Worker 使用独立 Worktree；
- 共享公共合同、同一文件、同一数据库/迁移、同一 Release Notes 或有强依赖 → 不支持直接并发，改为串行或 DAG 分阶段；
- 只做决策、调研、文档协调 → `coordination-only`，不创建代码 Worktree；
- 同一 Task 不拆给多个 Worker 同时写；拆分后必须声明 `depends_on`、`conflicts_with` 和 `exclusive_paths`；
- Coordinator 负责最终集成、影响测试、质量门禁和 Push，Worker 不直接 Push 共享分支。

## 测试路由

按风险选择最低但充分的层级：

- 纯选择、解析、校验、状态转换 → 单元测试；
- React 渲染、输入、点击、焦点、i18n、Jotai、路由 → 组件测试；
- IPC/RPC、Provider、Tool、事件、Schema、序列化 → 合同测试；
- Session、Runtime、Repository、生命周期和恢复 → 集成/生命周期测试；
- Electron、真实进程、文件系统、打包和网络边界 → 定向 E2E。

最低要求：

- Bug 修复：先有旧实现会失败的复现或明确基线，再有回归测试；
- 新功能或行为变化：覆盖一条用户常见完整流程和关键失败路径；
- 删除功能：覆盖入口消失、旧配置/数据回退和相邻功能保持；
- 性能任务：先记录基线，再以可重复指标验证改动；
- 取消、重试、并发、超时和资源释放：使用可控时钟和显式同步点，不使用任意 sleep。

Mock 只放在 Provider、网络、Electron、OS、外部进程和不可控时间等真实外部边界；内部协作者优先使用真实实现、内存存储或明确 Fake。

## 实施循环

1. **Red**：建立失败测试、复现或基线。
2. **Trace**：沿真实调用链确认根因和所有权。
3. **Change**：用最小、清晰、可回滚的实现修复根因。
4. **Green**：运行定向测试和代表性用户流程测试。
5. **Guard**：按仓库质量门禁运行 `check:quick`、影响测试和必要的完整 `check`。
6. **Record**：更新当前版本发布说明；长期架构决策才写 ADR，术语决策写 `CONTEXT.md`，调研和阶段计划写项目指定文档。
7. **Deliver**：说明可观察行为、主要文件、已运行与未运行的验证、剩余风险和兼容性影响。

## 完成标准

需求编译完成且允许实施，当且仅当：

- 意图和代码所有者明确；
- 当前行为和期望行为可区分；
- 必须保持的不变量已列出；
- 代表性用户流程和最低测试层级已选定；
- 重大歧义已解决或显式记录假设；
- 验证命令和发布说明要求已确定。

实现完成，当且仅当：

- 目标行为成立；
- 相关测试覆盖可观察合同；
- 失败、取消、重试、恢复和资源释放语义没有被静默破坏；
- 实际验证结果如实记录；
- 没有覆盖用户已有改动或执行未经授权的不可逆操作。
