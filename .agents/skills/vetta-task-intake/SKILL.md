# Open Forge 统一开发入口

## 工作合同

用户给目标、限制和验收反馈；Agent 承担工程决策与执行。不要把技术选型、文件清单、Given/When/Then、测试命令或任务拆分反向要求用户填写。“自主”不扩大发布、生产访问、真实 Provider/付费调用或破坏性操作的授权。

本入口负责编排，不复制专项规范：仓库根/最近一级 AGENTS 定义边界；[Project 规范](../../../project/CONVENTIONS.md)定义记录与状态；[vetta-testing](../../../.agents/skills/vetta-testing/SKILL.md)定义测试方法；[质量门禁](../../../docs/dev/quality-gates.md)定义命令；[协作流程](../../../project/collaboration/development-workflow.md)定义分支与集成。外部 Skills 只提供方法参考，不覆盖这些合同。

## 1. 先确认事实和执行范围

- `git status --short`，保留已有改动；读取最近规则、包 README、相关实现、测试与 ADR。当前行为以源码/类型/Schema/可执行脚本为准。
- 区分用户要求的是分析、计划、评审还是实施；“看看方案”不自动升级为写代码、提交或部署。
- 找到已有 REQ/PLAN/TASK/BUG 后续接，不为每个小改动新建整套文档。简单任务可先用三五行合同；复杂、跨模块或长期变更按 Project 规范记录。
- 根据真实文件、依赖与行为判所有者，不仅按关键词判断。若发现 Expo/EAS，先读本仓库 expo-overview 再做移动端选择；Go/Kotlin 使用目标包的工具链，不强行走 TypeScript 测试。

## 2. 自动选择主路线和必要支线

选择一个主路线，可组合真实相关的支线；不加载所有 Skills，不让用户选择框架。

| 任务信号 | 主路线与下一入口 | 交付证据 |
|---|---|---|
| 新功能、行为调整、删除 | 下面的薄切片实施 + vetta-testing | 常见操作流程、关键失败/兼容路径 |
| 报错、失败、回归、验收不通过 | 先复现→定位→修复；读取本仓库 diagnose | 旧行为失败的复现/测试与修复结果 |
| 重构、模块难维护 | 明确不变量与公开接口，先基线再调整 | 行为保持与依赖/职责改善 |
| 写测试、TDD、覆盖不足 | vetta-testing；TDD 是实施方式，不是另一套任务系统 | red/green 与用户流程对应 |
| CI/CD、构建、缓存、打包、发布准备 | [流水线路线](references/ci-cd.md)；失败同时走诊断 | 触发范围、执行图、产物与权限证据 |
| 慢、资源增长、并发退化 | 先可重复基线、主导瓶颈，再最小改动 | 相同条件下的前后指标 |
| AI 回答/工具行为/产物质量 | vetta-testing 的模型评估分层，必要时诊断 | 软件合同与模型质量分开报告 |
| UI、可访问性、交互 | 现有设计规则 + 组件/流程测试 | 渲染与事件接线；不默认启动 verify:ui |
| 协议、存储迁移、权限 | 生产者/消费者、兼容/回退；测试与安全支线 | 合同测试与授权边界 |
| 文档、调研、评审、仅计划 | 查第一方证据，按请求范围产出 | 来源、差异、风险；无行为变化不强制 TDD |

未知情况先调查最接近的真实入口，更新分类；不要把不确定任务硬塞进“新功能”。需要的领域 Skill 不可用时，使用仓库文档和现有测试推进；不自动联网安装技能、调用收费服务或静默略过验证。

## 3. 生成内部任务合同与自主决策

合同涵盖：目标/不做项、当前与期望行为、所有者、代表性用户流程、不变量、失败/取消/恢复、最低充分测试、验证命令、验收方式与并发结论。

事实由 Agent 自查。只有未决解释实质改变产品目标、公共合同、数据兼容、安全、费用、不可逆行为或无法自行取得必要输入时，才问一个关键问题并给出建议。已授权且合同明确的常规操作不反复索要授权；研究、实现或“自动化”请求也不视为新增发布授权。

先比较直接修改与必要重构：消除当前任务造成的重复事实源、错误职责或不可测试耦合；不为假想未来添加抽象。深模块追求小而稳定的接口与足够行为，不追求文件越拆越多。

功能按窄而完整的用户行为纵向切片，每片独立验证；行为保持型重构可先单独做，高扇出合同迁移采用 expand–contract 等既有兼容策略，不强行切成无法保持绿灯的层次任务。

## 4. 执行与纠偏

- 新行为/Bug：在 vetta-testing 指定的边界建立失败测试或明确基线，一片一片实现、验证，不先写全部测试再批量实现。
- 纯重构：先跑现有行为基线，调整后复验；测试难写若源于职责耦合，先建立可测试接缝。
- 性能/复杂系统：工程控制论 Skill 可按需辅助“分类→主导因素→最小工具→测量验证”。未建模、未识别参数时，不用 PID/稳定性术语宣称工程流程有数学保证。
- 每次反馈先区分自身回归、既有失败与环境阻断。重复失败但没有新证据时停止盲试，收集证据、调整假设或报告阻断；不删测试、不放宽门禁、不无限重跑。
- 并发由 Agent 按依赖和读写范围决定并简要告知用户；只有已获授权的多 Agent 工作才派工，真正并行写入使用独立 Task Worktree。共享合同或紧耦合任务串行，Coordinator 负责集成而非只收集完成总结。
- 命令按质量门禁选最小充分范围；完整 check 不代替测试，不默认全量构建，不使用真实用户状态做测试。

## 5. 工程交付与用户验收

执行 [交付与反馈闭环](references/delivery.md)：自动化检查、技术评审、人工功能验收分别记录。根据风险使用获授权的独立评审；不可用时如实注明自审，不冒称独立评审已完成。

工程完成后提供简短功能验收包，不把代码审核转交用户；用户尚未接受的功能 Task 保持 verifying。内部测试/文档任务可按已约定的自动化/文档标准关闭，不要求用户逐条人工点验，也不伪造产品验收。

用户拒绝验收时，把反馈重新编译为可复现行为或模型评估案例，修正并复验。开发候选集成不等于人工接受，更不等于稳定发布授权。
