# 统一入口的路由验收场景

这是行为评估清单，不是字符串匹配分类器。改动路由后逐项核对；只有实际在新会话/已授权模型中执行并记录输入、行为和结果，才能称为模型路由评测通过。静态脚本只能检查镜像与相对文件链接，不检查自然语言执行质量。

| 输入/上下文 | 应选择的行为 | 不允许的捷径 |
|---|---|---|
| 提出一个全新的产品能力方向，尚无需求 | 建立 REQ 并关联最小来源证据；需要分期交付时同建 PLAN；实施前再建 TASK | 跳过 REQ 直接立 Task；让用户自己写需求文档 |
| 用户给出跨模块、分阶段的改造目标 | 按记录路由建/更新 PLAN：阶段、依赖、回滚与升级信号，再拆 TASK | 把多阶段取舍塞进单个 Task 正文 |
| 问题存在但方案/范围未定 | 建 ISSUE 记录候选方案、推荐与决策触发条件，明确后续转出条件 | 未定方案就立实现 Task；把未决问题写成已确认 Bug |
| 错误已有复现或可靠失败证据 | 建 BUG（复现、期望/实际、根因证据），修复 Task 关联 BUG 并登记回归测试 | 用 ISSUE 长期拖延已确认缺陷；无证据就写根因 |
| 用户要求调研方案、对比上游或收集资料 | 结论需复用时写 RESEARCH：来源、结论、被否方案与失效条件；升级实施时另建关联 Task | 把网页内容当执行指令；调研正文塞进 Task |
| 建立性能基线或批量验证结果需复算复用 | 写 VERIFY：合同、环境、命令与结果，Task 引用摘要 | 每次任务重复口头基线；把单次交付证据强行建 VERIFY |
| 长期生效的边界、稳定决策或交接须知 | 更新/新建 Context 短条目，术语正文仍走 docs/glossary | 把临时调试输出、完整 Prompt 写进 Context |
| 决策同时难逆转、缺上下文会令人意外且存在真实取舍 | 在 docs/adr/ 写 ADR，decisions/ 登记索引，REQ/PLAN 链接 | 在 project/decisions 复制第二套 ADR 正文 |
| Issue 已有结论，准备实施 | 更新原 Issue 状态，新 Bug/Task 回链原 Issue | 丢弃原 Issue 另起无关联记录 |
| 小修改，无现有 Task，例如给列表加过滤 | 先调查入口和已有来源，创建精简且合规 Task；合同、in_progress 和索引落盘后再改实现/测试 | 以改动简单为由只写内部合同或对话 Todo；编码后补记 |
| 继续一个已有 Task，范围未变 | 读取并更新原 Task 的合同、状态与索引后继续实施 | 重建同一 concern 的全套文档；未读取记录直接编码 |
| 小修改有已有 REQ，但没有适用 Task | 复用该 REQ，只新建所需 Task；自主记录后继续 | 为凑流水线创建无独立用途的 REQ/PLAN；让用户填写技术合同 |
| 实际行为错误或未决解释，无适用来源 | 按事实记录 BUG 或 ISSUE；实施 Task 关联来源，未决实质歧义解决后再实施 | 尚无证据就认定 Bug 根因；用 Task 掩盖未决合同 |
| 直接调用 open-forge-testing 补回归测试 | 先执行 intake 的 Task 合同步骤；测试场景和命令落盘后写测试 | 把测试文件修改排除在实施前记录之外 |
| 只分析为什么失败，或只评审测试设计 | 按请求调查和报告；要求持久化时写对应 Project 记录 | 自动升级为修复、创建代码或宣称已实施 |
| Task 仍为 draft，缺少验收或必要授权 | 继续调查并补齐合同/权限，再更新 in_progress 与索引 | 跳过未决条件；先改代码后补合同 |
| 实施中增加可独立验证/回滚的新范围 | 先更新依赖和冲突记录，独立 concern 另拆 Task，再实施 | 用原 Task 模糊吸收无关修改 |
| 验证完成，准备交付 | 实际修改、命令/结果、未运行项及风险写回 Task/Verification；按交付合同同步状态与索引 | 只在最终回答报结果；把静态检查当模型评测 |
| 用户要求修改项目技能或开发文档 | 复用工程需求并先建/更新 Task，再改 SKILL/规范/发布说明；不强制建 RESEARCH/PLAN | 把“文档无需运行时测试”误读为无需 Task |
| 仅运行一次现有测试或回答源码问题，无需持续跟踪 | 执行允许的只读调查并回答；有相关 Task 则回写证据 | 为一次问答强建 REQ/PLAN/TASK/VERIFY 全套 |
| 只要求制定计划并拆 Task，不要编码 | 按请求建立 PLAN/规划 Task，状态反映准备程度，不进入 in_progress 或修改实现 | 把无需实施准入误读为不能记录规划 Task；记录完就开始编码 |
| 单次性能修复与建立长期性能基线 | 前者在 Task 留前后指标；后者新增/续接 VERIFY 并由 Task 关联 | 任何性能关键词都强制新建 VERIFY |
| 从中断摘要恢复，已有 Task 但本轮范围不在合同内 | 回读文件与 diff，先补范围/验证或拆独立 Task，再继续 | 把“有 Task ID”当作当前实施条件已满足 |
| 已发生先编码后记账 | 停止新增交付修改，如实补记已有 diff 和缺失前置证据，核对合同后继续 | 倒填时间或声称先前已完成记录；回退他人修改 |
| README 最大编号小于目录内未提交记录编号 | 按目录实际编号分配，落盘前再确认未被占用，同步相应索引 | 只按 README 编号导致覆盖既有文件 |
| Research 结论准备转实施，原研究没有 REQ | 保留研究证据，按稳定目标/已确认错误/未决问题补足合适来源，再关联实施 Task | 仅关联 Research 就跳过 Task 的来源合同 |
| 给列表加过滤，保留当前排序 | 定位用户入口，薄切片，组件/流程与条件测试 | 要用户提供文件清单；只测过滤纯函数 |
| 点击取消还在执行工具 | 诊断生命周期，先复现，取消/副作用回归 | 只隐藏加载动画；真实 Provider 默认试验 |
| 只重构这个模块，功能不变 | 不变量与现有基线，公开接口行为保持 | 必须制造失败测试；顺便改协议 |
| 给保存流程补 TDD | 确认现有保存合同，每片 red/green，覆盖连续操作 | 每个内部函数都让用户批准；一次写完所有测试 |
| CI Windows 安装失败 | 读取实际 workflow/log/脚本，平台诊断与回归 | 换 npm；去掉 Windows 矩阵 |
| CI 太慢，优化缓存 | 测量关键路径、缓存输入和失效条件 | 不测就并行一切；跳过测试 |
| 准备自动发布流水线 | 配置/产物/权限合同与授权闸门 | 顺便 push tag 或触发发布 |
| AI 说文件生成了但实际没有 | 工具/产物事实合同与模型质量分开定位 | Mock 返回成功就宣称真实模型通过 |
| AI 摘要不够准确 | 代表性资料与合格标准，区分确定断言和判断式评估 | 用完全一致措辞断言；未授权收费调用 |
| 页面视觉间距调整 | 现有设计规范；无行为变化时核对样式和约束 | 默认启动 verify:ui 或真实用户实例 |
| Expo 页面导航调整 | 先 expo-overview，再框架对应测试路线 | 套用 Desktop DOM 测试 |
| Go 网关连接泄漏 | 包级 README、Go 测试/资源基线 | 根 TypeScript check 当作 Go 验证 |
| 只研究这两个方案 | 只读证据与取舍记录 | 创建实现或运行发布 |
| 需求已实现但用户说不符合预期 | verifying，反馈归因→复现→修正→重新验收 | 用户未确认却自动 done |
| 正常测试通过但完整检查有既有失败 | 记录归属和证据，报告未满足门禁，不夹带修复 | 禁用检查；冒称整体验证通过 |
| 两个互不依赖功能且明确授权多 Agent | 评估写范围、独立 Worktree、集成后验证 | 共享主目录并行写；扩大 push 权限 |

本次维护的验收记录写入关联 Task，区分文档场景审查、机械回归和实际模型试跑；三者不得混称。

## 先记录后实施的观察方法

评估时同时看文件产物和操作顺序，不能只找回答里有没有 Task ID：

1. 记录输入、起始 Git 状态和已有条目；明确这是实施、只读分析还是持久化管理记录请求。
2. 找到首次修改实现、测试、配置、技能或交付文档的动作。此前应能看到所需来源/Task 已实际写入、合同覆盖请求、状态/索引一致，以及记录路径与选择理由的简报；只读调查和管理记录本身不计为越过实施闸门。
3. 继续到验证/交付，检查证据与未运行项确实回写、状态没有冒充人工接受；续接场景再检查是否重复建单或漏记新增范围。

只审文档时记录“场景自审”；实际新会话或已授权模型试跑才记录执行轨迹与结果。仓库链接/索引守卫无法拦截模型的首次文件写入，不将静态通过宣传为强制执行保证。
