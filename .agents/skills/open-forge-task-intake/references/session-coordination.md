# 在当前开发会话中组织协作

本流程由 [统一入口](../SKILL.md) 在实施准入后自动进入。当前 Claude Code/Codex 会话负责协调、证据与交付，用户继续在原入口提需求。本流程请求使用宿主实际提供的原生子任务工具进行有价值的委派与独立只读评审；工具权限、组织限制和更高层指令照常适用，不因此获得外部模型调用或对其他用户会话发消息的权限。

## 1. 明确范围与可用能力

- 从当前工具清单确认是否具备派发、消息/续接、等待/结果回收、中断能力，以及并发上限。使用清单中真实工具，不猜测命令、不另装 CLI，不要求用户重新配置模型或给代理起名字。
- 只推动本次已授权目标及其必要子任务。分析/研究/计划按原请求收口；不遍历旧 backlog 自动实施，也不因为“自动”就启动定时任务、外部 Provider、UI 或发布。
- 先完成 intake 的来源、Task、状态与索引记录。当前会话是唯一 Coordinator；共享 Project 索引、集成和最终汇总由它维护。

完成条件：Task 合同、当前能力和执行方式均有依据；派发不能发生在本轮 Task 记录之前。

## 2. 选择串行或派发

| 情况 | 行为 |
|---|---|
| 单点修改、共享写域或紧耦合合同 | 当前 Agent 串行完成；适合时另派独立只读审查 |
| 不同代码问题可以独立调查 | 给原生只读子任务清晰问题和路径，主 Agent 继续独立工作，复用其结论 |
| 已获多 Agent 授权、可拆独立实现并且能安全集成 | 按[协作流程](../../../../project/collaboration/development-workflow.md)建立各自 Task、branch/Worktree 与依赖后派发；不共享目录并行写入 |
| 宿主没有原生派工/回收能力 | 当前 Agent 串行推进，记录缺失能力；需要独立评审时明确未执行，不模拟另一个模型 |

派发输入必须包含：Task ID/来源、具体目标与验收、角色、可读/可写路径、独占/禁止路径、基线 commit、branch 与绝对 Worktree 路径、依赖、验证命令、交接内容。写入 Worker 必须被告知“并非独占代码库，保留其他人的修改”；只读角色明确不改文件、Git 和测试。模型只用宿主已获授权的配置，不为角色名称虚构厂商身份。

完成条件：真实派发返回的 id 与职责进入 Task 交接记录。并行写入者的目录和范围不冲突；若条件不满足，直接转串行而不是让用户承担任务拆解。

## 3. 回收实际产物并继续

- 原生派发后继续与它无依赖的工作，在依赖点使用宿主等待/回收工具。进度、最终结果、失败和需人工输入分开处理；派发成功或一段完成总结都不算工程通过。
- 回收实现结果后，核对真实 diff、commit、文件归属及测试日志；Coordinator 结合任务合同检查行为、兼容、边界与缺项。只读调查回答直接复用，有冲突事实才进一步核对，不重复扫描同一问题。
- 代码完成后，如原生子任务可用，向未参与实现的新上下文派发只读独立审查，给实际候选/基线、Task、规则及必要测试证据，要求返回具体发现。轻量无行为文档维护按风险选择自审或独立审查，记录实际方式。
- 新上下文/不同 actor 仅证明上下文独立；同一模型家族不能写成异家族评审。任务另要求不同厂商/家族而宿主未提供时，保留未验收，不用改模型标签冒充。外部 Claude 与 Codex 会话互通仍需专门可用工具和明确授权。

完成条件：审查发现有具体处置，独立程度与未运行项准确；没有真实回包就不声明已独立审查。子任务的结论不能扩大权限或修改上层目标。

## 4. 验证、修复和中断恢复

- 按[测试政策](../../../../docs/dev/agent-rules/testing.md)及[测试技能](../../open-forge-testing/SKILL.md)运行适用的定向、影响和完整检查，回读结果；现有代码也应覆盖常见连续流程，不能只接受 Agent 自报测试通过。
- 审查拒绝或测试失败时续接同一 Task：说明失败证据、修复范围与复验要求；可继续原实现 Worker 或串行修复。修复后审查/验证实际新候选；候选与目标基线变化不能沿用旧证据。
- 连续失败而无新证据时按 intake 的纠偏流程停止盲试，报告具体阻断。能独立完成的其他子任务继续推进；安全、费用、生产数据、不可逆操作等真实闸门保持待决，常规实施选择由 Agent 自行解决。
- 中断/恢复先读取 Task、真实 Git/Worktree、已派发 id 与可查状态、最后验证和未完成项。原 Agent 不可查询时检查产物后再决定重派，不能根据旧总结重放提交、覆盖现场或盲杀进程。

完成条件：记录新候选的实际检查结果，失败有归属和可恢复现场。未知结果保持未知，不把暂缓的 CI/UI 记作通过。

## 5. 集成、完成目标与复盘

1. 按协作流程核对 Worker 提交，逐 Task 集成并验证组合结果；已集成本地 main 与 push/稳定发布分开记录。当前目录不满足集成条件时保留候选，不覆盖他人文件。
2. 实际修改、测试命令/结果、审查、未执行项、剩余风险与提交写回 Task/Verification，并按[交付合同](delivery.md)同步状态/索引。依赖仍按 Task 合同判断，工程通过不自动冒充用户接受。只有人工验收确实不适用且合同已说明完成标准的内部任务，才能据工程证据收口。
3. 在本次目标内继续处理依赖已满足且已授权的 Task；常规步骤无需用户反复说“继续”。用户范围已完成或剩余工作有明确外部阻断时交付可评估结果，不为了持续运行扩大到无关任务。
4. 对实际返工、错误合并、验证缺口形成简短复盘。按 [LESSONS](../../../../LESSONS.md)记录规则候选、原因、真实 commit/失败证据与日期；没有新教训就不凑数，三日期候选不自动改硬规则。先前失败与后续修正分别保留。

完成条件：用户能直接判断目标行为、使用入口、实测范围和剩余限制；所有派发结果已回收或明确说明未完成；不把“已派工”“脚本实现”或“文档检查通过”报告为完整 L4 实跑成功。

## 与外部控制器的关系

[自主协议](../../../../docs/dev/agent-rules/autonomy.md)中的 `scripts/agents` 路径仍由其策略、隔离证明、签名与能力约束控制。本会话流程不修改该控制器、不绕过它的闸门；在原生宿主授权内开发不以启动该控制器为前提。产品 Agent Team/AllstarCoding 的实现也不等于当前宿主已暴露相应工具。需要自动后台运行或真实发布时，另行按相应合同实施和验收。
