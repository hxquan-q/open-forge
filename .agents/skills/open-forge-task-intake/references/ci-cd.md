# CI/CD：在既有流水线内形成反馈

仅在任务涉及流水线、构建、缓存、打包、依赖安装或发布准备时读取。CI 验证与 CD 发布是不同权限，修改 workflow 不等于授权触发发布。

## 先识别实际系统

读取目标 workflow、它调用的 package scripts/composite actions、目标包 README、质量测试和失败日志。绘制最小执行图：事件/路径→依赖安装→检查/测试→必要构建→产物→发布闸门。以文件为准，不复制通用 Skill 的 npm、Jest、旧 Actions 版本或全量构建示例。

区分配置错误、代码回归、runner/网络波动、缓存污染、平台差异。若只能取得部分日志，报告证据缺口，不能假装本地通过就证明远端成功。

## 变更路线

1. 记录受影响事件、分支/路径筛选、needs、矩阵、权限、缓存键、产物消费方和预期失败行为。
2. 先补能失败的配置/脚本合同测试，或建立当前失败基线；正常路径和拒绝/失败路径都要覆盖。
3. 在既有脚本和 workflow 中修复，不新建并行的“第二套 CI”。减少耗时须有测量，优先去重安装、正确缓存和无依赖步骤并行，不减少平台/测试覆盖换取绿灯。
4. 用仓库 runner 执行定向质量脚本测试，再按影响运行门禁。仅在风险需要时本地构建目标产物；实际远端 CI、平台矩阵、签名和发布若未运行，明确标为未验证。
5. 提供功能层验收：什么事件会运行什么检查、错误会如何阻断、产物从哪里取得，以及哪些步骤仍需授权。

## 不能静默改变的边界

- 不删除必需检查、改低阈值、跳过失败测试或把失败改成 continue-on-error 来“优化”。
- PR/外部代码不接触发布凭据；不为外部 PR 扩大 token 权限，不把不可信输入拼入 shell。
- 缓存须考虑 OS/架构/锁文件/工具链与生成物输入，不让陈旧声明、原生依赖或来源不可信的缓存掩盖失败。
- 校验修改后的权限最小化、并发取消和产物关联，避免旧任务发布覆盖新任务。
- 遵守既有 main→origin/dev→origin/main 流程。tag、Release、registry、部署或真实收费任务须有对应明确授权；用户要求“修 CI”不包含这些动作。
