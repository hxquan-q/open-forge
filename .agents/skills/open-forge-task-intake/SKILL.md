# Open Forge 统一开发入口

## 入口闸门：先记录，后实施

进入任何实施路线或交给专项技能修改文件前，先完成第 1 节调查和第 3 节记录；第 2 节只用于选路线，不构成直接编码许可。文档/技能维护和直接补测试同样适用。只读问答按请求回答，需要沉淀的计划/调查按 Project 记录路由落盘，不因此获得实施授权。

## 工作合同

技术选型、文件清单、Given/When/Then、测试命令和任务拆分由 Agent 从仓库事实推导。职责、验收状态及反馈规则统一见 [交付合同](references/delivery.md)。

本入口负责编排，不复制专项规范：仓库根/最近一级 AGENTS 定义边界；[Project 规范](../../../project/CONVENTIONS.md)定义记录与状态；[open-forge-testing](../../../.agents/skills/open-forge-testing/SKILL.md)定义测试方法；[质量门禁](../../../docs/dev/quality-gates.md)定义命令；[协作流程](../../../project/collaboration/development-workflow.md)定义分支与集成。外部 Skills 只提供方法参考，不覆盖这些合同。

用户在 Claude Code/Codex 提出开发目标后，当前会话担任 Coordinator，负责把已授权目标推进到交付。实施任务完成第 3 节准入后，必须继续执行[原生会话协作](references/session-coordination.md)：选择串行或原生子任务、回收产物、审查、验证、修复与收尾，不以交出计划或派出 Agent 作为完成。外部 `scripts/agents` 是另一条显式启动路径，其默认关闭状态不要求用户为当前会话重新配置模型 API；实际宿主权限继续生效。

## 1. 先确认事实和执行范围

- 项目已有 `.ua` 或 `.understand-anything` 时，先按[知识图谱调查](references/knowledge-context.md)读取元数据、架构层和目标子图，检查 Git 增量后回读相关源码。图谱是导航数据；缺失、过期或缺少某节点时继续查源码，不重建图谱作为开发前提。

- `git status --short`，保留已有改动；完整读取根与最近一级 AGENTS，按根路由加载匹配的规则扩展，再读包 README、相关实现、测试与 ADR；规则注入被截断时从文件读取完整正文。当前行为以源码/类型/Schema/可执行脚本为准。
- 区分用户要求的是分析、计划、评审还是实施；“看看方案”不自动升级为写代码、提交或部署。
- 读取 [Project 入口](../../../project/README.md)、[管理规范](../../../project/CONVENTIONS.md)和目标记录目录 README，检索已有 REQ/PLAN/TASK/BUG/ISSUE/RESEARCH/VERIFY，确认本次 concern 的来源与归属；按管理规范的“记录路由”自主选择要创建或更新的文档类型并实际落盘，不让用户挑选；简单任务也进入持久化 Task。
- 调查阶段可只读源码、检索记录和运行已有测试基线；按记录路由判断是否需要持久化研究或计划，转实施前完成下面的 Task 合同。
- 根据真实文件、依赖与行为判所有者，不仅按关键词判断。若发现 Expo/EAS，先读本仓库 expo-overview 再做移动端选择；Go/Kotlin 使用目标包的工具链，不强行走 TypeScript 测试。

## 2. 自动选择主路线和必要支线

选择一个主路线，可组合真实相关的支线；不加载所有 Skills，不让用户选择框架。每条路线的交付证据同时包含记录路由要求建立的 Project 条目（第 3 节）。

| 任务信号 | 主路线与下一入口 | 交付证据 |
|---|---|---|
| 新功能、行为调整、删除 | 下面的薄切片实施 + open-forge-testing | 关联来源的 Task、常见操作流程、关键失败/兼容路径 |
| 报错、失败、回归、验收不通过 | 先复现→定位→修复；读取本仓库 diagnose | 按事实关联缺陷/问题记录、旧行为失败的复现/测试与修复结果 |
| 重构、模块难维护 | 明确不变量与公开接口，先基线再调整 | Task 记录的行为保持与依赖/职责改善证据 |
| 写测试、TDD、覆盖不足 | open-forge-testing；TDD 是实施方式，不是另一套任务系统 | red/green 与用户流程对应，结果回写 Task/VERIFY |
| CI/CD、构建、缓存、打包、发布准备 | [流水线路线](references/ci-cd.md)；失败同时走诊断 | 触发范围、执行图、产物与权限证据 |
| 慢、资源增长、并发退化 | 先可重复基线、主导瓶颈，再最小改动 | Task 或关联 VERIFY 中相同条件下的前后指标 |
| AI 回答/工具行为/产物质量 | open-forge-testing 的模型评估分层，必要时诊断 | 软件合同与模型质量分开报告 |
| UI、可访问性、交互 | 现有设计规则 + 组件/流程测试 | 渲染与事件接线；不默认启动 verify:ui |
| 协议、存储迁移、权限 | 生产者/消费者、兼容/回退；测试与安全支线 | 合同测试与授权边界；必要时 ADR |
| 文档/技能维护、调研、评审、仅计划 | 查第一方证据，按请求范围产出 | 维护交付文件先建/更新 Task；研究/计划按记录路由落盘，无行为变化不强制 TDD |

未知情况先调查最接近的真实入口，更新分类；不要把不确定任务硬塞进“新功能”。需要的领域 Skill 不可用时，使用仓库文档和现有测试推进；不自动联网安装技能、调用收费服务或静默略过验证。

## 3. 按记录路由建立文档，再进入实施

先按 [Project 规范的记录路由](../../../project/CONVENTIONS.md#记录路由选择哪种文档)补齐来源记录，再完成 Task 合同：

1. 按 Project 记录路由选择本次最小文档组合，读取命中目录的 README 及其模板后实际创建或更新文件；记录类型、转换和关联以该规范为准，不在技能内维护第二套分类。已有同主题条目续接，编号以目录内现有文件为准；仅分析/计划时按请求完成适用记录（可含规划 Task）后交付，不因记录完成而进入实施；以下步骤用于已要求实施的工作。
2. 读取并续接同一 concern 的现有 Task；没有合适 Task 时，按目标目录 README 与 [Task 模板](../../../project/tasks/templates/task.md)新建，关联上一步确定的 REQ、BUG 或 ISSUE 来源。简单修改复用已有来源并精简正文，不机械生成全套文档。
3. 将目标/不做项、当前与期望行为、Owner、输入输出及依赖、Given/When/Then、不变量、适用的失败/取消/恢复路径、最低充分测试、验证命令和验收方式写入 Task。详细测试合同或证据可放关联 Verification，Task 保留摘要与链接。
4. 写明并发结论、执行方式、读写/独占路径、依赖和冲突、branch/worktree 及集成状态。并行能力评估不等于获得多 Agent 授权；执行方式遵循协作流程。
5. 核对所有新增/更新记录满足模板及目录索引要求，Task 合同满足 ready 标准且必要授权已解决；开始实施前更新为 in_progress，同步 Task 当前焦点表。写入后回读 Task 与索引，确认文件真实存在、来源关联有效、合同覆盖本次范围、状态一致，而不是仅凭写入命令或历史总结判断完成。
6. 在首次交付文件编辑前向用户简报：新建/续接的记录 ID 与路径、选择该组合的理由、目标与并发结论。例如“复用 REQ-xxxx，已创建 TASK-yyyy（路径）；单一修改无需 PLAN，串行实施”。这是落盘结果报告，不是等待用户批准的检查点；对话计划、工具 Todo 或内部推导不能替代记录。

事实由 Agent 自查。只有未决解释实质改变产品目标、公共合同、数据兼容、安全、费用、不可逆行为或无法自行取得必要输入时，才问一个关键问题并给出建议。已授权且合同明确的常规操作不反复索要授权；任务记录完成后自主继续，不新增记录审批。研究、实现或“自动化”请求不视为新增发布授权。

先比较直接修改与必要重构：消除当前任务造成的重复事实源、错误职责或不可测试耦合；不为假想未来添加抽象。深模块追求小而稳定的接口与足够行为，不追求文件越拆越多。

功能按窄而完整的用户行为纵向切片，每片独立验证；行为保持型重构可先单独做，高扇出合同迁移采用 expand–contract 等既有兼容策略，不强行切成无法保持绿灯的层次任务。

**允许实施**：用户要求实施，相关 Task 合同已落盘、状态为 in_progress 且索引同步；目标行为和所有者明确，不变量及最低验证路径已确定，实质歧义与必要授权已解决。首次修改实现、测试、配置或交付文档前核对这些条件；未满足时先调查和补齐记录。仅分析、计划或评审时按请求范围交付，不自动进入实施。

## 4. 执行与纠偏

本节沿[原生会话协作](references/session-coordination.md)持续执行，直到当前目标工程交付或遇到有证据的阻断。原生派工由当前宿主实际工具完成；缺少相应能力时串行推进独立工作并记录未执行的评审，不伪造派发、跨工具互通或独立模型结果。

- 新会话、中断恢复或从其他技能转入时，回读当前 Task、索引和实际 diff；旧 Task 的存在或上一轮总结不等于当前范围已获记录。若发现已先改文件后记账，先停止新增交付修改，如实补记现有 diff、缺失的前置证据和后续验证计划，完成第 3 节后继续；保留他人修改，不倒填记录或声称顺序合规。
- 每个切片开始前核对 Task 范围；目标、依赖、冲突路径或验证方式变化时先更新记录，独立新增 concern 另拆 Task。验证命令、结果和失败归属及时记入 Task 或关联 Verification，供中断续接和交接复核。
- 新行为/Bug：在 open-forge-testing 指定的边界建立失败测试或明确基线，一片一片实现、验证，不先写全部测试再批量实现。
- 纯重构：先跑现有行为基线，调整后复验；测试难写若源于职责耦合，先建立可测试接缝。
- 性能/复杂系统：可选的 `engineering-cybernetics-essence` Skill（不随仓库分发，需执行环境已安装）可按需辅助“分类→主导因素→最小工具→测量验证”。不可用时仍按仓库的基线/指标方法执行；未建模、未识别参数时，不用 PID/稳定性术语宣称工程流程有数学保证。
- 每次反馈先区分自身回归、既有失败与环境阻断。重复失败但没有新证据时停止盲试，收集证据、调整假设或报告阻断；不删测试、不放宽门禁、不无限重跑。
- 并发由 Agent 按依赖和读写范围决定并简要告知用户；只有已获授权的多 Agent 工作才派工，真正并行写入使用独立 Task Worktree。共享合同或紧耦合任务串行，Coordinator 负责集成而非只收集完成总结。
- 命令按质量门禁选最小充分范围；完整 check 不代替测试，不默认全量构建，不使用真实用户状态做测试。

## 5. 工程交付与用户验收

**工程完成**：目标行为与保留合同有实际证据，适用测试及门禁通过，必要文档与当前版本发布说明已更新，验证结果/未运行项/剩余风险已记录。必需验证失败时不能宣称工程完成。

按 `apps/desktop/package.json` 的 version，依照 [发布说明规范](../../../.github/release-notes/README.md) 补写当前开发版本的 `.github/release-notes/v<version>.md`；不改已发布正文、不触发发布。

随后执行 [交付合同](references/delivery.md)：将实际修改、验证命令/结果、未运行项及原因、风险和提交/集成事实写回 Task 或关联 Verification，再按实际事实更新状态与导航索引，提供验收包。分别记录工程、集成、人工接受与发布；用户尚未接受功能时保持 verifying。验收反馈关联原 Task 重新进入诊断或实施，独立新增范围另拆 Task。

## 维护与验证

`.agents/skills/open-forge-task-intake` 和 `open-forge-testing` 是唯一权威正文；Claude 通过 `.claude/skills` 共享链接读取。Devin 镜像已移除，使用能读取 `.agents` 的环境。运行 `node scripts/quality/workflow-skills.mjs` 只读检查；不再提供 `--write` 或同步 API，也不重新创建副本。

[路由验收场景](references/scenarios.md)用于人工/已授权模型验证。静态源文件与链接检查只证明文件合同，不证明模型一定会正确分类或完整执行。设计来源与适用边界见 [RESEARCH-0017](../../../project/research/RESEARCH-0017-development-paradigm-synthesis.md)。
