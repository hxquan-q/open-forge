# AP 开发执行（环节手册 · lite）

> 读者可能是主会话本体（inline 执行）或通用子代理（spawn 执行，契约即全部输入）。两种读者都按本手册独立完成本环节。

**第 0 步（自检，仅主会话读者执行）**：通用子代理读者跳过本步——计划行由主会话管理，你的契约就是环节指令。主会话读者：若本会话尚未输出工作流计划行（`[工作流] …`），先按 `ap-router` 的规则路由并补一行再继续（用户直接下达的明确单点小任务可免）。

目标：按需求要点（有 design.md 则按其改动面清单）完成编码并自测通过。**代码改动落项目根**（不落辅助工作区）；报告与中间产物落 `<工作区>/pipeline/<slug>/`。

## 1. 开工前勘察（对齐项目，别按想象写）

| 勘察项 | 手段 |
|---|---|
| 项目类型与工具链 | 读 README / package.json / 依赖清单 |
| 结构 | 列顶层与相关子目录 |
| 既有规范 | 读 AGENTS.md / docs/（有则必遵） |
| 相关既有实现 | 搜索需求关键词（是否已有部分实现） |
| 测试现状 | 找测试文件与测试命令 |

## 2. 改动面清单（>3 文件必做，写进报告）

改动超过 3 个文件时，动第一行代码前先列文件级清单（有 design.md 则核对/收窄它的清单）：

| 操作 | 文件 | 内容 |
|------|------|------|
| 新增/修改/删除 | `src/<path>` | <一句话> |

**执行顺序**：被依赖者在前（dto→service→controller）；"签名改动与调用方同步"是**一件事**不拆开；每完成一个文件项目处于可编译/可运行状态，不留半成品跨步骤。

## 3. 实现纪律

1. **循既有模式**：用项目已有的工具函数、惯例、错误处理方式；只有一个简单实现且无真实变化点时不新增抽象/接口。
2. **边界处理**：空值、错误路径、异常输入照既有惯例处理，不静默吞。
3. **不越范围**：发现范围外问题记入报告"风险"节，不顺手修；不删看似多余的校验/兼容代码，存疑先报告。
4. **平台陷阱**：Windows 路径分隔符与长路径；PowerShell `>` 重定向默认 UTF-16（落盘用框架 outputFile 或显式 utf8）；npm/pnpm 缓存目录 EPERM 时把 cache 指进工作区。
5. **git 纪律**：不 commit 不 push，改动留在工作区（提交由用户决定）。

## 4. 自测（完成编码后必做）

1. 跑与改动相关的**既有测试**——选最快的**定向测试命令**（单文件/单目录/相关标签），不默认跑全量套件；失败 → 修复 → 重跑，直到通过或证明与改动无关（后者报告里给证据）。
2. 新增行为按需求要点 A#（或契约 validation）逐条自查。
3. **调用链自查**（交付前过一遍）：
   - [ ] 新代码的入口/出口/注册点/配置引用全部接上
   - [ ] 删除/重命名的符号全仓无残留引用
   - [ ] "必须同步"关联点（design.md S 条目）逐项完成
   - [ ] 无范围外文件被改动
4. 测试跑不起来（依赖装不上/环境崩）→ 记"受阻项"，**不为跑通改测试或加 skip**。

## 5. 汇报结构（inline 交付用户 / 子代理最终报告同构）

```
已完成: <文件清单 + 每处一句说明>
自测结果: <跑了什么命令、结果；A#/validation 逐条状态>
受阻项: <工具被拒/需越域/环境失败，无则写"无">
风险: <发现的隐患与范围外问题，无则写"无">
```

**交付即停**：自测通过、汇报完毕即本环节结束，不自动进入测试环节（按计划行等下一环节指令）。

子代理执行时：受阻不重试不绕路（沙箱/权限被拒原样记录），按 `ap-contract` 汇报合同回报，由主会话转达用户。
