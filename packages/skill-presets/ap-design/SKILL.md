# AP 设计要点（环节手册 · lite）

> 读者可能是主会话本体（inline 执行）或通用子代理（spawn 执行，契约即全部输入）。两种读者都按本手册独立完成本环节。

**第 0 步（自检，仅主会话读者执行）**：通用子代理读者跳过本步——计划行由主会话管理，你的契约就是环节指令。主会话读者：若本会话尚未输出工作流计划行（`[工作流] …`），先按 `ap-router` 的规则路由并补一行再继续。

目标：把已确认的需求要点翻译成**可执行的实现方案**——改哪些文件、怎么改、有什么风险。产物：`<工作区>/pipeline/<slug>/design.md`（一页）。本环节不写业务代码。

**受众**：开发者。写"监听计算按钮点击，收集两个输入与运算符，执行计算，结果写结果区"这种粒度。

## 1. 前置勘察（五项，比需求环节深一层）

| 勘察项 | 手段 | 回答什么 |
|---|---|---|
| 改动面定位 | 顺着需求条目逐条找入口/出口/调用链 | 每条需求动哪些文件（新增/修改/删除） |
| 既有模式 | 读改动面邻近代码 | 项目怎么写这类东西（风格/工具函数/惯例） |
| 接口影响 | 搜索被改函数/类型的所有使用处 | 签名变化波及谁 |
| 数据与状态 | 追数据流 | 新数据放哪、旧数据怎么兼容 |
| 测试锚点 | 定位既有测试文件 | 每条改动在哪补测试 |

## 2. 方案决策

每个独立决策点：**候选方案 → 取舍 → 结论**。倾向最小改动与既有模式复用；引入新依赖/新抽象必须给理由。多个合理方案且影响大 → 列开放问题留给用户。

## 3. design.md 模板（一页）

```markdown
# 设计要点：<需求名>
更新: <日期>　上游: requirements.md（<状态>）

## 方案总览
<三到五句：做什么、整体思路、为什么不选别的>

## 架构决策
| # | 决策 | 候选 | 结论与理由 |

## 改动面清单（文件路径级）
| 操作 | 文件 | 内容 |
|------|------|------|
| 新增 | `src/<path>` | <模块职责> |
| 修改 | `src/<path>` | <改什么> |

**必须同步修改的关联点**（开发时不得遗漏）：
- S1: 改 `<file>` 的 X 签名 → 同步 `<调用方>` 的 N 处调用

## 风险
| 风险 | 触发条件 | 缓解 |

## 测试锚点
单元/集成锚点（文件路径级）+ 用户视角重点
```

## 4. 填写规则

1. **改动面文件路径级精确**——开发环节直接照此执行。
2. **"必须同步"关联点单列**——漏同步是结构破坏的主因，宁多勿漏。
3. 多文件任务给**执行顺序**：被依赖者在前（dto→service→controller）；每个文件做完项目可编译运行（增量可验证）。
4. 决策保留候选记录——争议时回看取舍。

## 5. 完成判定

- [ ] 改动面清单覆盖全部需求条目，路径级精确
- [ ] 每个决策有候选与理由；开放问题已列
- [ ] "必须同步"关联点逐条列出（无则写"无"）
- [ ] design.md 落盘，向用户/主会话交付路径+方案总览一句话，**交付即停**

子代理执行时：判定通过后按 `ap-contract` 汇报合同回报。
