# AP 原型 + 需求要点（环节手册 · lite）

> 读者可能是主会话本体（inline 执行）或通用子代理（spawn 执行，契约即全部输入）。两种读者都按本手册独立完成本环节。

**第 0 步（自检，仅主会话读者执行）**：通用子代理读者跳过本步——计划行由主会话管理，你的契约就是环节指令。主会话读者：若本会话尚未输出工作流计划行（`[工作流] …`），先按 `ap-router` 的规则路由并补一行再继续。

目标：把用户的想法变成**看得见、点得通的原型** + **一页需求要点**，让用户在写代码前确认"要做的东西对不对"。产物：`<工作区>/pipeline/<slug>/prototype.html` 与 `requirements.md`。L1（仅原型环节）用精简版 requirements.md：只保留 R# 需求条目、F# 字段清单与开放问题（A#/范围外省略——字段级标注是仅原型交付的核心内容，不省）。

**受众铁律**：原型与需求要点只写业务、只写用户看得见的东西。技术细节（文件/函数/表/框架）一律不出现——那是设计环节的事。

## 1. 源材料解读

用户给了 Excel/截图/既有页面等材料时：

| 材料 | 怎么读 | 落到哪 |
|---|---|---|
| Excel 表 | 逐 sheet 逐列：列名→字段（F#）、示例值→类型/取值线索、合并单元格/公式→取值方式 | 字段清单 F# + 原型表格列 |
| 截图/图片 | 界面区块→界面名、控件→字段与操作（R#） | 界面结构 + R# |
| 既有页面/系统 | 保留的行为写 R#（依据标"既有"），新行为标"新增" | R# 依据列 |

拿不准的业务取舍（枚举值、默认值、字段是否必填）→ 标 `【推断】` 并收进 requirements.md 的开放问题节，**不要替用户拍板**；能在原型确认时一并问的就攒到那时问。

## 2. HTML 原型规范（prototype.html）

1. **单文件自包含**：内联 CSS/JS，无外部依赖（无 CDN、无构建、无图片资源引用），双击即开。
2. **核心界面 + 主流程可点通**：呈现主要界面（页面/弹窗/关键状态），主流程能走——按钮有响应、页面可切换、输入可填写；假交互用简单 JS 模拟（点击显示预设结果也算合格）。
3. **R# 标注**：每个交互元素带编号角标（R1、R2…与需求条目对应），用户能精确指认（"R3 这个按钮位置不对"）。
4. **字段取值标注（能标就标）**：承载业务数据的输入/展示控件尽量带 `<类型>:<取值方式>` 标注（如 `基础资料:用户手动选择`、`2位小数:应发数量-已发数量`），用词与 §4 字段清单词表一致，用业务语言。载体：输入框写 placeholder；不支持 placeholder 的控件在紧邻处放灰字；明细表格标注放表头单元格（整列共享）。装饰性/纯导航元素不标；放不下不硬标（清单里有即可）；拿不准就标。placeholder 填值后会看不见——标注同时写进 title（悬停可见）或提供"重置演示数据"按钮，二选一。
5. **计算字段尽力联动演示**（改应发/已发，未发实时重算）；做不了时标注照写，联动留给开发。
6. **视觉可糙，逻辑要对**：不追求美观，追求流程结构正确（几个界面、怎么跳、关键反馈是什么）。移动端需求 viewport 适配；桌面端默认 1200px 宽。

## 3. 需求条目（R#，业务流程链）

| # | 需求 | 类型 | 依据 |
|---|------|------|------|
| R1 | 谁→在哪→做什么→看到什么结果 | 功能 | 用户原话 /【推断】/ 既有行为 |

每条可验收：写"能做到什么"，不写"怎么实现"。推断必标。

## 4. 字段清单（F#，与原型标注一一对应；纯流程无字段时省略）

| # | 所属界面 | 字段 | 类型 | 取值方式 |
|---|---------|------|------|---------|
| F1 | <界面名> | 物料 | 基础资料 | 用户手动选择 |

- 类型词表：`基础资料 / 整数 / N位小数 / 金额 / 百分比 / 文本 / 长文本 / 日期 / 日期时间 / 枚举`。
- 取值方式词表：`用户手动选择 / 用户手动填写 / 从源单携带 / <计算公式> / 系统自动 / 默认值(<值>)`。
- 新词可加，须业务自明；原型标注与清单用词一致。

## 5. 验收标准（A#，与 R# 对应，用户视角可观察）

- [ ] A1（对应 R1）：按步骤操作后的可观察结果

可判性要求：写成"打开 X，点击 Y，看到 Z"，不写"运行正常"。A# 是后续测试环节的种子。

## 6. requirements.md 模板（一页，别超）

```markdown
# 需求要点：<需求名>
更新: <日期>　状态: 草案 | 已确认（<日期>）

## 目标
<一句话：做完后什么变好>
## 需求条目（R#）
<§3 表格>
## 字段清单（F#）
<§4 表格，无则删节>
## 验收标准（A#）
<§5 清单>
## 范围外
<明确不做的，一句话>
## 开放问题（无则删）
- Q1: <问题> → 建议 <方案>（待用户定）
```

## 7. 交付与确认

产物落盘后向用户输出：产物路径 + 要点摘要（≤5 行：几个界面/几张表/几个开放问题）+ 一句收尾。**不弹确认卡、不搞全文朗读仪式。**收尾话术按计划行分两种：

- **L2/L3（计划行含后续环节）**——这是唯一默认确认点，交付即停等回复："确认后继续 <下一环节> / 要改请说（R# 指认）"。用户确认 → 本环节完成，后续按计划行继续；回复修改 → 改完重新交付。
- **L1（仅原型，无后续环节）**——交付即停，不诱导续做："要改请说（R# 指认）；需要进入开发另说。"

## 8. 完成判定

- [ ] prototype.html 落盘且双击可开、主流程可点通
- [ ] 每个交互元素有 R#，业务字段有 F# 标注（或已在清单）
- [ ] requirements.md 一页内（L1 精简版：R# + F# + 开放问题）
- [ ] 推断全部标【推断】，开放问题已列
- [ ] 已按 §7 话术交付并按档位停住（L1 交付即停；L2/L3 等确认）

子代理执行时：以上判定通过后在最终报告按 `ap-contract` 汇报合同回报，不直接找用户确认——确认由主会话转达。
