# AP 测试（环节手册 · lite）

> 读者可能是主会话本体（inline 执行）或通用子代理（spawn 执行，契约即全部输入；spawn 执行自带独立视角，优于作者自测）。两种读者都按本手册独立完成本环节。

**第 0 步（自检，仅主会话读者执行）**：通用子代理读者跳过本步——计划行由主会话管理，你的契约就是环节指令。主会话读者：若本会话尚未输出工作流计划行（`[工作流] …`），先按 `ap-router` 的规则路由并补一行再继续。

目标：验证**基本功能可运行**——**速度优先，不追求穷尽覆盖**。流程：**健康总检 → 用例执行 → 用户视角核验表**，全程分钟级预算。产物：`<工作区>/pipeline/<slug>/test-report.md`。

## 1. 测试范围（从三处派生）

1. 需求要点验收标准（A#）——逐条要有覆盖
2. design.md 测试锚点（有则用）
3. 改动面邻近的既有功能——回归重点

## 2. 项目健康总检（先于逐用例，三项必查）

| # | 检查项 | 方法 | 判定 |
|---|---|---|---|
| P1 | 结构完整 | 改动清单声明的文件全部存在；无任务外孤儿文件 | 缺失/孤儿 → 严重 |
| P2 | 正常启动 | **最快可行验证**：用项目最小启动命令/最小构建确认"能起"（dev server/服务进程/脚本可跑即可）；**禁止默认跑全量构建链与全量测试套件** | 失败 → 严重 |
| P3 | 邻近冒烟 | 挑改动面邻近的既有核心功能 2-3 条跑通 | 挂 → 严重 |

P 项任一严重 → 先报后再继续（修复优先于逐用例）。证据要求：命令输出贴报告，不口头断言。

## 3. 用例设计

- **可执行优先**：能落成命令/脚本/操作步骤的不写"人工感觉一下"。
- **核心路径优先**：目标=验证基本功能可运行，不是穷尽覆盖——核心路径全写，边缘只挑代表。
- **三重心**：①业务逻辑正确性（A# 派生）②整体运行稳定（启动、连续操作、异常输入不崩）③新旧接洽（回归）。
- **粒度**：总数 ≤10 条，一屏可扫。
- 每条注明来源（A# / 回归 / 稳定性）。
- 能自动执行的自动执行（浏览器可自动化就自动化）；不能的进 §5 用户核验表。

## 4. 执行纪律

1. **速度纪律**：测试命令**优先选定向子集**（与目标相关的单文件/单目录/相关标签的既有测试命令）；全量套件**仅当用户点名**才跑。整个测试环节以**分钟级**为预算，预估超时 → 收窄范围（抽样或降为冒烟）并在报告说明——绝不允许出现单环节小时级耗时。
2. 测试命令后台跑、输出**落盘**再读（`--reporter=json --outputFile=` 或重定向文件），避免管道捕获陷阱。
3. Windows 下 PowerShell `>` 重定向默认 UTF-16 会误判 binary——用框架 outputFile 或 `Out-File -Encoding utf8`。
4. 环境级跑不起来（装依赖失败/框架崩）→ 记"受阻项"，不算测试失败。
5. 失败不中断：跑完全部用例再统一报告。
6. 严重度分级：**严重**（调用链断/逻辑错/崩溃/验收不达标）、**一般**（非核心路径失败/边界缺失）、**轻微**（警告/风格）。verdict：任一严重 → fail；无严重但一般 ≥3 → fail；否则 pass。

## 5. 用户视角核验表（黑盒精华：用户能执行、能核验）

每条 = 明确操作步骤 + 预期现象，不需要看代码：

```markdown
### B<n>: <用例名>（来源）
- 测试操作: 1. … 2. …
- 预期: <可观察现象>
- 结果: ✓ / ✗（→P#）/ 豁（理由）
```

自动化覆盖的用例记录结果即可；**未能自动化的关键路径进此表交用户核验**（交付时点出：请重点过目 B# 清单）。

## 6. test-report.md 模板

```markdown
# 测试报告：<任务名>
更新: <日期>　verdict: pass | fail

## 健康总检
| P1/P2/P3 | 结果 | 证据摘要 |

## 用例结果
| # | 用例（来源） | 结果 | 说明 |
（✓/✗/豁；✗ 指向 P#）

## 问题清单（P#）
- P1: [严重/一般/轻微] <现象> · 复现: <步骤/次数> · 状态: 待修/已修/未修（理由）

## 用户核验表
<§5 格式的未能自动化条目>

## 受阻项 / 豁免（无则删节）
```

## 7. 修复循环

1. verdict=fail（或 P 项严重）→ 修复：inline 任务直接改；子代理产物用 `followup_task(<task_name>, <问题清单>)` 召回修。
2. 修完**只复测受影响用例**，不全量重走。
3. 循环 ≤3 轮；超限停下，把分歧（测试结论 vs 修复回应）整理上报用户裁决。
4. 问题根源在上游（需求/设计错了）→ 停下报告，不擅自改上游产物。

## 8. 完成判定

- [ ] P1/P2/P3 全过（证据在报告；P2 为最快可行验证，非全量构建）
- [ ] 全部用例执行完毕（✓/✗/豁，豁免有理由）
- [ ] 测试执行为**定向子集**（非全量，全量仅用户点名）；范围收窄/降为冒烟时已在报告说明
- [ ] 无未解决 [严重]；[一般] 清零或已向用户明示遗留
- [ ] test-report.md 落盘；交付时给用户：verdict 一句 + 失败/豁免条目 + 核验表请重点过目项

子代理执行时：判定通过后按 `ap-contract` 汇报合同回报（含 verdict 与 P# 摘要），核验表由主会话转达用户。
