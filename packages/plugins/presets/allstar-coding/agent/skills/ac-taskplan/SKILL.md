# AC 任务清单拆分（流水环节 6-7）

目标：把 design.md 的改动面拆成**任务清单**——按依赖链排序派发，**且保证每个任务环节执行完成后项目都可编译运行**（增量可验证切分：任务边界不落在"半成品"上）。产物 `docs/ac/tasks.md`。主控以此调度开发子。

**执行者分工**：拆分策略（依赖排序、并行组划分）由主控定；tasks.md **写作由任务子完成**（spawn 一次性，写域仅 `docs/ac/tasks.md`，T1 文件允许档）；产出后主控跑 §6.4 覆盖性自检。

**改动面字段要求（v0.4 新增）**：任务卡的「任务」条目必须**文件路径级**列出改动面——它就是开发子契约 scope 的直接来源（scope glob 从这里逐条摘出，V3/V4 硬校验的输入）。改动面写不细，下游 scope 就拼不准。

## 环节 6：拆分原则（任务子遵守）

### 6.1 任务粒度（四条全满足）

1. **自包含**：一个干净子代理读完任务卡（+ 上游产物路径）就能开工；
2. **可独立验收**：完成判据明确（评审子能逐条打勾）；
3. **增量可验证**：完成后项目处于一致状态（编译过、相关测试过），**不留半成品跨任务**——这是硬性要求：任务边界若切在"接口已定义、实现还没写"上，中间状态编译不过即违规；
4. **大小适中**：预估改动 ≤ ~10 文件或一个内聚主题；超了就拆。

### 6.2 排序规则

- **按依赖链排序**：被依赖者在前。例：controller 依赖 service，service 依赖 dto → 顺序：先 dto，再 service，再 controller。
- 无依赖的任务可标 `并行组`（主控可并行派发）。
- **"必须同步"关联点不得与本体分离**——签名改动与调用方同步是**一个**任务；太大时在同一任务内列子步骤。
- 依赖关系必须无环。

### 6.3 任务卡字段（每任务必填）

```markdown
## T<n>: <任务名>
- 依赖: 无 | T<m>
- 并行组: 无 | G<k>
- 输入: docs/ac/design.md §<节>; <其他上游文件>
- 任务: <逐条列出，文件路径级——改动面清单；开发子契约 scope 从此摘出>
- 验收标准: <逐条可检查；尽量写成可执行判据——"X 文件存在"、"npm test 退出码 0"、"构建成功"，评审子会实际执行贴输出；静态判据与命令判据分开列>
- 风险提示: <给开发子的特别提醒（平台陷阱、既有雷区），无则省>
```

### 6.4 覆盖性自检（主控在任务子产出后必做）

对照 design.md 逐项核对：
- [ ] 改动面清单每一行都落在某个 T 的任务里
- [ ] 每个"必须同步"关联点（S 条目）都在同一 T 内有对应条目
- [ ] 测试策略的每个锚点都有对应 T（或并入相关 T 的验收标准）
- [ ] 依赖关系无环
- [ ] 每个 T 单独完成后项目可编译运行（增量可验证）

漏一条就打回任务子补，核对不过不出清单。

## 环节 7：可选确认门

- 默认：**≤3 个任务 → 跳过**，告知用户清单摘要后直接开工（state.md 记 skipped）。
- 建议开启：任务 ≥4 或含并行组、含高风险任务、用户要求。
- 机制：按 ac-pipeline §0.1 协议（先落盘 → 对话区完整输出 tasks.md → 极简确认卡）。

## 产出后（主控）

1. 落盘 `docs/ac/tasks.md`（头部状态标记 + 修订记录）。
2. 主控把每个 T 建为 todo（T 间依赖在内容注明），进环节 8 逐个推进。
3. state.md 更新：环节 6/7 done → currentStep 8；开发循环建为父环节、各 T 为 subSteps（每个 T 一个 step 对象，executor: developer，agentRef 留待 spawn 后回填）。
4. 环节 6/7 收口（ac-gate 校验）→ 打 stage 档（`stage 7/任务清单: tasks.md 定稿`，经轻量 git 子代理 + V4，§0.5）。
5. **开工顺序**：按依赖拓扑序起开发子；并行组可一次起齐（各自 durable id 记 state.md）。

## 边界提醒

- tasks.md 是**执行合同**：开发子只对任务卡负责，任务卡外的改动属越权（评审维度 3 的检查点）。
- 任务清单本身变更（执行中发现遗漏/需增删）：主控修订 tasks.md 并记修订记录；影响已完成任务的，回到该任务的评审逻辑补验。
