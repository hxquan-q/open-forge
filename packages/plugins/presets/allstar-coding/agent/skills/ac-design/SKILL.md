# AC 开发评估与开发文档（流水环节 4-5）

目标：把已批准的需求文档（requires.md）翻译成**可执行的实现方案**——技术框架、改动面、实际代码实现逻辑。产物 `docs/ac/design.md`。本环节不写业务代码。

**受众定义**：开发文档面向**开发者**。例：计算器 → "监听计算按钮点击事件，触发时收集两个文本框输入区+一个计算符选择区的值，执行对应计算，将结果输出到结果区，刷新页面"。

**执行者分工**：勘察、方案取舍与写作**全部由架构子完成**（spawn 一次、常驻挂起，修订用 followup_task 唤醒；写域仅 `docs/ac/design.md`，T1 文件允许档）。主控只拼指针式任务书（上游 requires.md 路径 + 批准状态 + 下放的勘察清单/决策纪律）并 spawn、收报告；开放问题经「待主控处理」节带回，主控代问用户。

## 环节 4：架构评估（架构子，随任务书下放；主控只 spawn 与收口）

以下勘察五项、决策原则与风险评估全部随任务书下放给架构子执行，产出写进 design.md 对应节（改动面清单/架构决策表/风险表——与 §5.1 模板逐节对齐），供任务子与评审子自读；主控不做这些动作。

### 4.1 方案设计前置勘察（架构子执行，比需求阶段更深一层）

| 勘察项 | 手段 | 回答什么 |
|--------|------|----------|
| 改动面定位 | 顺着需求条目逐条找入口/出口/调用链 | 每条需求动哪些文件（新增/修改/删除） |
| 既有模式 | 读改动面邻近代码 | 项目怎么写这类东西（风格/工具函数/惯例） |
| 接口影响 | grep 被改函数/类型的所有使用处 | 签名变化波及谁 |
| 数据与状态 | 追数据流 | 新数据放哪、旧数据怎么兼容 |
| 测试锚点 | 定位既有测试文件 | 每条改动在哪补测试 |

### 4.2 方案决策

每个独立决策点：**候选方案 → 取舍 → 结论**。倾向最小改动与既有模式复用；引入新依赖/新抽象必须给理由。多个合理方案且影响大的 → 开放问题留给确认门。

### 4.3 风险评估

逐条：风险 → 触发条件 → 缓解。重点：行为变化对既有调用方的破坏、平台差异（Windows 路径/编码/行尾）、性能、数据兼容。

## 环节 5：产出开发文档（架构子）

### 5.1 design.md 模板

```markdown
# 开发文档：<需求名>

状态: 待确认 | 已批准（<日期>，<门方式或"跳过">）
更新: <时间>
上游: docs/ac/requires.md（已批准版本）

## 1. 方案总览
<三到五句：做什么、整体思路、为什么不选别的。>

## 2. 架构决策
| # | 决策 | 候选 | 结论与理由 |
|---|------|------|-----------|

## 3. 改动面清单（按子系统分组）
### 3.x <子系统名>
| 操作 | 文件 | 内容 |
|------|------|------|
| 新增 | `src/<path>` | <模块职责> |
| 修改 | `src/<path>` | <改什么> |
| 删除 | `src/<path>` | <删什么，调用方去向> |

**必须同步修改的关联点**（任务清单必须逐项包含）：
- S1: 改 `<file>` 的 X 签名 → 同步 `<调用方文件>` 的 N 处调用

## 4. 接口与数据变更
- 公共 API / 数据格式 / 无变更则写"无"

## 5. 失败模式与风险
| 风险 | 触发条件 | 缓解 |
|------|----------|------|

## 6. 测试策略
- 单元/集成锚点（文件路径级）/ 白盒重点（调用链验证点）/ 黑盒重点（用户可感知行为）

## 7. 分阶段建议（给任务清单的输入）
| 阶段 | 内容 | 依赖 | 建议验收 |
|------|------|------|----------|

## 修订记录
| 日期 | 反馈 | 修改 |
```

### 5.2 填写规则

1. **改动面文件路径级精确**——任务清单、开发子任务书、评审子对照全部以此为准。
2. **"必须同步"关联点单列**——结构破坏（评审维度 3）的主要来源，宁多勿漏。
3. 架构决策保留候选方案记录——评审争议时回看取舍是否成立。
4. 测试策略直接派生白盒/黑盒用例——验收标准（requires.md）↔ 测试锚点双向对照。
5. 分阶段建议粒度：每阶段 = 一个可独立验收、可交给一个干净开发子会话完成的工作包。

## 可选确认门（环节 5）

- 默认：需求简单/改动面小 → **跳过**，直接进任务清单（告知用户跳过了，给一句方案摘要，state.md 记 userConfirmation: skipped）。
- 建议开启（满足其一）：新增依赖；跨 ≥3 个子系统；接口/数据格式变更；删除或重命名公共符号；用户明确要求。
- 开启时按 ac-pipeline §0.1 协议执行（先落盘 → 对话区完整输出 → 极简确认卡）。批准后标 `已批准`。

## 交接

- design.md 定稿（门开启时批准 / 跳过时按默认）→ 环节 4/5 收口（ac-gate 校验）→ 打 stage 档（`stage 5/开发文档: design.md 定稿`，经轻量 git 子代理 + V4，§0.5）→ 进环节 6（ac-taskplan）；改动面清单与分阶段建议是任务清单的直接输入。
- state.md 更新（环节 4/5 完成 → currentStep 6）。
- **给任务清单的硬约束**：design.md 里每个"必须同步修改"的关联点，任务清单必须显式包含对应任务，不许靠开发子自觉。
