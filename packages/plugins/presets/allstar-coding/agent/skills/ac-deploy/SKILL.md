# AC 部署（流水环节 12）

目标：前述流程全部通过后，由部署子执行：**提交专用 git 分支 → 等待专人合并完成并构建产物 → 拉取最新产物 → 更新对应服务**。部署策略：每步先走用户确认，确认后尽量自动执行；自动执行失败即上报，不盲目重试。

**执行者**：部署子（spawn 一次性）。任务书由主控按本技能拼装；产物部署记录追加 state.md。

## 1. 部署四步（部署子顺序执行）

### 1.1 专用分支提交

1. 检查流水分支状态（git status / log 只读）：全部改动已在流水分支（收尾环节会做最终提交，这里做的是**部署提交**——若部署流程要求改动先在一个专用部署分支，则从流水分支创建 `deploy/<日期>-<需求slug>`）。
2. 按项目提交惯例写提交信息（无惯例则：`deploy: <需求名>（流水 <round> 轮）`）。
3. **不 push 远程**——push 与合并由用户/专人执行（铁律）。

### 1.2 等待合并（用户门）

1. 主控告知用户：「部署提交已就绪于分支 `<branch>`，请安排专人合并与构建产物」。
2. ask_user_question 卡：`已合并并构建完成` / `合并遇阻（说明）` / `取消部署`。
3. 等待期间不轮询；用户确认后继续。

### 1.3 拉取最新产物

1. 按项目实际方式拉取构建产物（git pull 专用目录 / 下载制品 / CI 产物目录——以 design.md 或用户指示为准）。
2. 校验产物完整性（文件存在、大小非零、版本号符合预期）。
3. 拉取失败 → 上报主控（附命令与输出原文），不重试超过一次。

### 1.4 更新对应服务

1. 按项目部署方式执行更新（重启服务 / 替换文件 / 运行部署脚本——以 design.md 或用户指示为准）。
2. **更新前**：向用户确认（ask_user_question：「即将执行 <命令清单>，是否继续？」）——这是不可逆操作门。
3. **更新后验证**：服务起来后验证关键变更点生效——至少核对 requires.md 验收标准中最可视化的一条。
4. 验证失败 → 上报；轻则回修复循环（白盒小循环），重则建议回滚（git revert 类操作交用户执行）。

## 2. 部署子任务书要点（主控拼装）

- history：流水已全部通过、部署是最后环节
- current_state：分支名、改动清单摘要、design.md 的部署相关节
- objective：四步全部完成或明确卡在哪一步
- scope：部署分支与产物目录；**不改业务代码**
- constraints：不 push 远程；每步执行前按 §1 的门确认；自动执行失败上报不盲目重试；遵循项目既有部署惯例
- deliverables：部署记录（各步命令、输出摘要、验证结果）追加 state.md（由主控代写）
- validation：服务更新后关键验收点生效

## 3. 越权与失败处理

- 部署子被沙箱拒绝的操作 → 记"待主控处理" → 主控交辅助者预审代办。
- 任一步自动执行失败：部署子停止、上报现状（已完成到哪步、失败命令与输出）；主控与用户协商——重试 / 手动执行 / 回退。
- 部署后问题（服务异常）→ 回白盒修复循环（小循环），修复后重新走受影响的部署步骤。

## 4. 完成后

- state.md：环节 12 done（部署记录：分支、提交哈希、产物版本、验证结论）。
- 交接 ac-finalize（环节 13 收尾）。
