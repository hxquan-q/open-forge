# AC 需求评估与原型+需求文档（流水环节 1-3）

目标：把用户的大概需求变成 **HTML 原型 + 配套需求文档**——原型让用户"看见"要做的东西，需求文档让用户逐条确认行为。产物 `docs/ac/originModel.html` 与 `docs/ac/requires.md`，经用户确认门（环节 3）后定稿。

**受众铁律**：原型与需求文档只涉及**业务逻辑、面向用户**。例：需求是计算器 → 需求文档写"输入1，输入+，输入1，点击计算按钮，输出2"。技术细节（文件/函数/表/框架）一律不出现——那是 design.md 的职责。勘察照做（要懂项目才能写对需求），但勘察的技术结论只用于支撑判断，不进文档正文。

**执行者分工**：勘察与澄清由主控做（要跟用户来回）；原型与需求文档**写作由需求子完成**（spawn 一次性）——写域：`originModel.html` + `requires.md` + `docs/ac/prototype/**`（原型配套资源如多页 HTML/外链 js/图片在 prototype/ 下自组织，进 artifacts 清单）。主控把勘察结论与澄清结果整理进自包含任务书（契约 schema v2，ac-pipeline §0.2）交它执笔。

## 环节 1：需求评估与勘察（主控）

### 1.1 项目勘察清单（写文档前必做）

| 勘察项 | 手段 | 回答什么 |
|--------|------|----------|
| 项目类型与技术栈 | 读 README / package.json / 依赖清单 | 这是什么项目、怎么构建测试 |
| 结构 | glob 顶层与相关子目录 | 模块怎么分、改动落在哪 |
| 既有规范 | 读 AGENTS.md / docs/ | 有没有必须遵守的规则 |
| 相关既有实现 | grep 需求关键词 | 需求是否已有部分实现 |
| 测试现状 | 找测试文件与测试命令 | 白盒阶段跑什么 |
| 版本状态 | git log 最近提交（只读） | 项目活跃度 |

勘察结论进任务书的 current_state 节（文件路径级），让需求子可溯源。

### 1.2 需求澄清

- 含糊需求：**能勘察回答的不问用户**；只有用户能定的才问（业务取舍、优先级、范围边界），ask_user_question 一次问全。
- 用户原始输入不脑补扩大；合理推断标 `【推断】`，确认门时提请用户注意。

## 环节 2：产出原型 + 需求文档（需求子）

### 2.1 HTML 原型规范（originModel.html）

原型是**静态可交互 HTML 单文件**，让用户在浏览器里点开就走一遍核心流程：

1. **单文件自包含**：内联 CSS/JS，无外部依赖（无 CDN、无构建、无图片资源引用），双击即开。
2. **核心界面 + 主流程**：呈现需求涉及的主要界面（页面/弹窗/关键状态），主流程可点通（按钮有响应、页面可切换、输入可填写）——假的交互用简单 JS 模拟（点击计算按钮显示预设结果也算合格）。
3. **标注系统**：每个交互元素带编号标注（R1、R2…与需求条目对应），用户反馈时能精确指认（"R3 这个按钮的位置不对"）。
4. **视觉可糙，逻辑要对**：不追求美观（配色排版从简），追求**流程结构正确**（几个页面、怎么跳转、关键操作的反馈是什么）。
5. 移动端需求用 viewport 适配；桌面端需求默认 1200px 宽布局。

### 2.2 需求文档规范（requires.md）

```markdown
# 需求文档：<需求名>

状态: 草案 | 待确认 | 已批准（<日期>，ask_user_question 确认）
更新: <时间>

## 1. 目标
<一句话：做完后什么变好。>

## 2. 现状（业务视角）
- 项目是做什么的 / 相关既有功能（用户能看到的现状行为）/ 规范约束

## 3. 需求条目（业务流程链）
| # | 需求 | 类型 | 依据 |
|---|------|------|------|
| R1 | <谁→在哪→做什么→看到什么结果，如"输入1，输入+，输入1，点击计算按钮，输出2"> | 功能 | 用户原话/【推断】 |

## 4. 验收标准（与 R# 一一对应，用户视角可观察）
- [ ] A1（对应 R1）：<按步骤操作后的可观察结果>

## 5. 范围外
- <明确不做的，原因>

## 6. 开放问题
- Q1：<问题> → 建议：<方案>（待用户定）（无则删本节）

## 修订记录
| 日期 | 门反馈 | 修改 |
```

填写规则：
1. 通篇假设读者不懂开发——出现文件路径/函数/数据表/框架名即为越位。
2. 每条需求可验收：写"能做到什么"，不写"怎么实现"。
3. 需求条目与原型标注编号一一对应（R1 ↔ 原型里的 R1 标注）。
4. 推断必标注；验收标准是白盒/黑盒用例的种子。

## 环节 3：用户确认门（必经，主控执行）

按 ac-pipeline §0.1 协议：
1. 原型与需求文档落盘（状态 `待确认`）。
2. 对话区完整输出需求文档全文 + 告知原型文件路径（用户双击打开核对交互）。
3. ask_user_question 弹卡：「原型与需求文档已输出，是否批准进入架构环节？」选项：批准 / 需要修改（R# 指认修改点）。
4. 需要修改 → 需求子修订（可 followup_task 唤醒原会话，修订处标【修订】）→ 重新输出 + 再弹卡。
5. 批准 → 两文档标 `已批准`，state.md 更新（环节 3 done），进环节 4。

**规则**：用户口头同意不算过关——必须走确认卡。批准后的需求实质变更（影响范围/验收标准）→ 重新过门。

## 交接

批准后：两文档标 `已批准` → 环节 3 收口（ac-gate 校验）→ 打 stage 档（`stage 3/需求确认门: 需求文档定稿`，经轻量 git 子代理 + V4，§0.5）→ 告知用户进入架构环节（4），并提示：开发文档确认门是可选的（默认小改动跳过，开启条件见 ac-design）。
