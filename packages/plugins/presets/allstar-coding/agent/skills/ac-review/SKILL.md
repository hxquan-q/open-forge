# AC 任务评审（流水环节 8 · 评审侧）

目标：定义**评审子怎么评、verdict 怎么出、评审记录怎么落盘对账、打回怎么走**。评审子 = `spawn_agent` 的 **general 型**、契约 scope 仅 `docs/ac/reviews.md`，每任务一个，不复用、不与开发子共享上下文——独立无偏由「新起会话 + 写域唯一 + V2/V4 双链审计兜底」保障（不再依赖 explorer 机制只读）。

## 1. 委派评审（主控）

1. 开发子 settlement 通知到达 → 从其最终报告取"已完成"清单。
2. spawn_agent（general 型，task_name 如 `review_t1`，契约 scope：`docs/ac/reviews.md`）发起评审，任务书含：
   - **评审对象**：tasks.md 的 T<n> 节（任务卡全文）+ 开发子报告的改动清单
   - **依据**：design.md 相关节路径 + requires.md 验收标准（A#）
   - **评审维度**：§2 四维
   - **输出格式**：§3 verdict 规范
   - **证据要求**：必须实际打开改动文件核对——报告说改了什么不算数，文件里真改了才算。可执行判据（文件存在/命令退出码）实际执行贴输出；执行受限记"未验证"而非 pass。
   - **写域**：评审子的整理规划与评审记录落点是 `docs/ac/reviews.md`（追加制，ac-pipeline §0.4）——不是 review-log.md（旧名弃用），更不是其他 docs/ac/ 文件。verdict 由评审子**自行落盘**，主控只对账（G4：最新节 verdict == 口头回报），不代写。
3. 复评（打回后）：**新起评审子**，任务书附上轮问题清单，要求逐条对状态（已修/未修/新引入）。首个评审附：tasks.md 对 design.md 改动面/「必须同步」项的覆盖性复核（ac-taskplan §6.4 清单）。

## 2. 评审维度（四维 + 硬检查，逐项过）

| 维度 | 检查什么 | 证据 |
|------|----------|------|
| 0 产物完备性（硬检查） | requires/design/tasks 三文档存在且非空 | 命令输出贴报告（每次必跑） |
| 1 调用链完整性 | 新代码上下游接全：入口/出口/调用方/被调方/注册点/配置引用 | grep 调用点逐个在位；删除/重命名符号全仓无残留引用 |
| 2 业务逻辑正确性 | 实现符合需求与开发文档；边界/空值/错误路径处理 | 对照 requires 验收标准 + design 语义；平台差异（Windows） |
| 3 结构破坏 | 未越任务卡范围；未破坏既有结构（无关文件、签名变化未同步、删除在用物） | git diff 范围核对 + design"必须同步"清单逐项 |
| 4 验收标准差距 | 任务卡验收条目逐条核对（可执行判据实际执行） | 每条给出 通过/差距/未验证 |

证据规则：每个 fail 结论必须带 文件:位置；"感觉有问题"不算，要"看到 X 处 Y 与 Z 不符"。

## 3. verdict 规范（评审子输出格式，写进任务书）

```
verdict: pass | fail
问题清单:（fail 时必填）
- [严重] <文件:位置> <问题> → <修正建议>
- [一般] ……
- [轻微] ……
逐维度小结: 5 行，每维一句
复评说明（若为复评）: 上轮问题逐条状态（已修/未修/新引入）
```

判定规则：
- **任一 [严重] 未解决 → fail**。[严重] = 调用链断、逻辑错误、结构破坏、验收条目不达标。
- [一般] 存在但无 [严重] → 可 pass，问题清单原样转开发子（下一任务顺带修或记 reviews.md）。
- [轻微] → pass，记录即可。
- **意见不确定时倾向 fail**：宁可多一轮打回，不放过带病任务（但打回理由必须可验证，不猜）。

## 4. 打回流程（主控执行）

1. verdict=fail → 完整问题清单通过 `followup_task(dev_t<n>, ...)` 转达同一开发子会话，格式：问题清单 + "逐条修复后回报，不要求解释，要求修复或说明为何不能修"。
2. 开发子修正 settlement → 新起评审子复评（附上轮问题清单）。
3. 计数：同一 T 打回轮次 ≥1 记 reviews.md 与 state.md（executions+1）；上限 3 轮（ac-pipeline §0）——达上限仍 fail 停止，把分歧（评审意见 vs 开发者回应）整理上报用户裁决。
4. verdict=pass → reviews.md 记录该 T 通过（含遗留 [一般]/[轻微] 项），state.md 更新（subStep done、sessionStatus suspended），T 档存档（ac-dev §4.5），进下一 T。

## 5. reviews.md 评审记录规范（追加制，ac-pipeline §0.4）

评审子写域落地为轻量节格式（防写飞的最小约束）：

```markdown
## T<n> · 第 <轮> 评审
verdict: pass | fail
问题清单:（fail 必填；[严重/一般/轻微] 文件:位置 问题 → 建议）
证据:（静态判据引用 file:line；命令判据引用主控预跑输出）
```

- **追加不清空**：天然形成评审史；`<T编号, 轮次>` 双键与 state.md 的 executions 计数严格对账；复评任务书直接引用上节原文。
- **verdict 对账钩子**：主控收口时核对「reviews.md 最新节 verdict == 评审子口头回报 verdict」——不一致以落盘为准，按越权处置 SOP 记录（ac-pipeline §0.6）。
- 每轮一行摘要可另记表格（历史兼容格式）：

```markdown
## T<n> 评审记录
| 轮次 | verdict | 严重/一般/轻微 | 摘要 |
|------|---------|----------------|------|
| 1 | fail | 2/1/0 | 调用链缺注册；已打回 dev_t1 |
| 2 | pass | 0/1/0 | 修复确认；遗留 1 一般项记入待办 |
```

## 6. 边界

- 评审子只评不改：写域仅 `docs/ac/reviews.md`（自留地）；问题经主控转达，不直接给开发子留言。写其他任何文件 = 越权，V2 双链校验会抓（mtime 链抓「改了没提交的」）。
- 评审对象是**当前 T 的改动**；上轮遗留 [一般] 项的修复情况在复评说明里带一句。
- 评审子自身出错（工具被拒/超时）→ 主控重起评审子，不计打回轮次。
