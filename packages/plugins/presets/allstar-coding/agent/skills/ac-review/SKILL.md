# AC 任务评审（流水环节 8 · 评审侧）

目标：定义**评审子怎么评、verdict 怎么出、打回怎么走**。评审子 = `spawn_agent` 的 **explorer 型**（机制级只读：read/grep/glob），每任务一个，不复用、不与开发子共享上下文——独立无偏。

**能力分界（证据分层的根基）**：explorer 评审子**没有 shell、没有 git、没有 MCP**——它做不了命令执行类验证。因此验证证据分两层供给：

- **静态判据**（文件存在/内容核对/引用链 grep）：评审子用自身工具自证。
- **命令类判据**（测试退出码/构建结果/git 范围）：由主控供给——委派评审**前**预跑（§1.5），评审中发现遗漏按 §1.6 补证。

## 1. 委派评审（主控）

1. 开发子 settlement 通知到达 → 从其最终报告取"已完成"清单。
2. **主控预跑证据（spawn 评审子之前，必做）**：
   - 任务卡（T<n> 节）里全部**可执行验收判据**逐条代跑（如 `npm test`、构建命令、存在性 `node -e` 检查——做法同 ac-gate G1），原始输出（含退出码）留存。
   - `git status --porcelain` + `git diff --stat`：当前改动的文件清单快照（维度 3 的范围证据）。
3. spawn_agent（explorer 型，task_name 如 `review_t1`）发起评审，任务书含：
   - **评审对象**：tasks.md 的 T<n> 节（任务卡全文）+ 开发子报告的改动清单
   - **依据**：design.md 相关节路径 + requires.md 验收标准（A#）
   - **主控预跑证据**：§1.2 的全部命令输出与 git 快照，原样贴进 relevant_context
   - **评审维度**：§2 四维
   - **输出格式**：§3 verdict 规范
   - **证据要求**：静态判据必须实际打开改动文件核对（read/grep/glob）——报告说改了什么不算数，文件里真改了才算。命令类判据以任务书内主控预跑输出为准，不得凭空推断其结果。
4. **补证回路**：评审中发现判据既无静态证据可查、又缺主控预跑输出 → 该条记 `未验证` 并列入 verdict 的 `待执行清单`（§3），**不因未验证直接判 fail**。主控收到后：简单只读命令自己跑；复杂/写操作命令 `team_delegate_task` 交辅助者（经其安全预审）执行 → 输出作为 followup 补给评审子 → 只复评该条。
5. 复评（打回后）：**新起评审子**，任务书附上轮问题清单，要求逐条对状态（已修/未修/新引入）。

## 2. 评审维度（四维 + 硬检查，逐项过）

| 维度 | 检查什么 | 证据来源 |
|------|----------|----------|
| 0 产物完备性（硬检查） | requires/design/tasks 三文档存在且非空 | 评审子用 ls/read 自证（引文件大小或内容首行为证），或以任务书内主控预跑输出为准 |
| 1 调用链完整性 | 新代码上下游接全：入口/出口/调用方/被调方/注册点/配置引用 | 评审子 grep 调用点逐个在位；删除/重命名符号全仓无残留引用 |
| 2 业务逻辑正确性 | 实现符合需求与开发文档；边界/空值/错误路径处理 | 评审子对照 requires 验收标准 + design 语义读文件比对；平台差异（Windows） |
| 3 结构破坏 | 未越任务卡范围；未破坏既有结构（无关文件、签名变化未同步、删除在用物） | 对照任务书内主控预跑的 git status/diff 快照逐项核对任务卡范围 + design"必须同步"清单逐项 |
| 4 验收标准差距 | 任务卡验收条目逐条核对 | 静态判据评审子自证；命令类判据以主控预跑/补证输出为准；每条给出 通过/差距/未验证（附待执行清单） |

证据规则：每个 fail 结论必须带 文件:位置；"感觉有问题"不算，要"看到 X 处 Y 与 Z 不符"。

## 3. verdict 规范（评审子输出格式，写进任务书）

```
verdict: pass | fail
问题清单:（fail 时必填）
- [严重] <文件:位置> <问题> → <修正建议>
- [一般] ……
- [轻微] ……
逐维度小结: 5 行，每维一句
待执行清单:（存在未验证条目时必填，否则省略本行）
- <判据原文> → 原因: <缺命令输出/缺 git 快照/其他>
复评说明（若为复评）: 上轮问题逐条状态（已修/未修/新引入）
```

判定规则：
- **任一 [严重] 未解决 → fail**。[严重] = 调用链断、逻辑错误、结构破坏、验收条目不达标。
- **未验证条目不计为通过，也不单因未验证判 fail**——列待执行清单等主控补证；补证后只复评该条，不整轮打回。
- [一般] 存在但无 [严重] → 可 pass，问题清单原样转开发子（下一任务顺带修或记 review-log）。
- [轻微] → pass，记录即可。
- **意见不确定时倾向 fail**：宁可多一轮打回，不放过带病任务（但打回理由必须可验证，不猜——"缺证据"走待执行清单，不算可验证的 fail 理由）。

## 4. 打回流程（主控执行）

1. verdict=fail → 完整问题清单通过 `followup_task(dev_t<n>, ...)` 转达同一开发子会话，格式：问题清单 + "逐条修复后回报，不要求解释，要求修复或说明为何不能修"。
2. 开发子修正 settlement → 新起评审子复评（附上轮问题清单 + 补证后的判据输出）。
3. 计数：同一 T 打回轮次 ≥1 记 review-log.md 与 state.md（executions+1）；上限 3 轮（ac-pipeline §0）——达上限仍 fail 停止，把分歧（评审意见 vs 开发者回应）整理上报用户裁决。**补证回路不算打回轮次**（它没有触发开发子修正）。
4. verdict=pass → review-log.md 记录该 T 通过（含遗留 [一般]/[轻微] 项），state.md 更新（subStep done、sessionStatus suspended），进下一 T。

## 5. review-log.md 格式

```markdown
## T<n> 评审记录
| 轮次 | verdict | 严重/一般/轻微 | 摘要 |
|------|---------|----------------|------|
| 1 | fail | 2/1/0 | 调用链缺注册；已打回 dev_t1 |
| 2 | pass | 0/1/0 | 修复确认；遗留 1 一般项记入待办 |
```

## 6. 边界

- 评审子只评不改（explorer 机制只读）；它也不执行命令——命令类证据一律由主控供给（预跑或补证）。
- 评审子是主控的私有子代理，不是团队成员：它没有 team_delegate_task/team_send_message，无法直接找辅助者——补证一律经主控中转。
- 评审对象是**当前 T 的改动**；上轮遗留 [一般] 项的修复情况在复评说明里带一句。
- 评审子自身出错（工具被拒/超时）→ 主控重起评审子，不计打回轮次。
