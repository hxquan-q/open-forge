# AC 黑盒测试（流水环节 10-11）

目标：白盒通过后，出具**带状态的黑盒测试文档**，指导用户对实现需求及其涉及改动面进行测试确认。黑盒是必经用户门（环节 11）。

**执行者**：blackbox.md 由黑测子产出（spawn 一次性，写域仅 `docs/ac/blackbox.md`，T1 文件允许档)；反馈处理与修复循环由主控驱动（followup_task 唤醒开发子）。

## 1. 文档设计原则（黑测子）

- **用户能执行**：每条用例 = 明确操作步骤 + 预期现象，不需要用户看代码。
- **覆盖三重心**（用例分组）：
  1. **业务逻辑正确性**——requires.md 验收标准（A#）派生的用户可感知场景
  2. **整体运行稳定**——启动、常规操作连续使用、异常操作不崩
  3. **新旧功能接洽**——本次改动涉及区域的既有功能回归（design.md 改动面邻近行为）
- **带状态**（本设计特定）：每条用例带状态字段，用户反馈后原地更新（不删旧记录）：
  ```
  ### B1: <用例名>（对应 A1）
  - 前置: <环境/数据准备，无则省>
  - 步骤: 1. <在哪、做什么> 2. ……
  - 预期: <应看到什么>
  - 状态: 待测 | 通过 | 失败（现象: ）| 豁免（理由: ）
  ```
- **粒度**：核心路径全写，边缘挑代表；总用例 10-20 条（一屏可扫）。
- 每条标注来源（A# / 回归 / 稳定性），与白盒用例呼应但不重复（白盒测不到的"用户感知"才是黑盒价值）。

## 2. 交付用户（主控）

1. blackbox.md 落盘，状态 `待执行`。
2. 主控向用户简报：测试重点、预计耗时、如何反馈（按用例编号 B# 说结果，或贴现象/截图描述）。
3. **等用户**——这是必经门（不催，用户可能要花时间）。反馈收集也走 ask_user_question 卡（选项：全部通过 / 有失败项（编号+现象）/ 环境不具备需调整）。

## 3. 反馈处理

| 反馈 | 处理 |
|------|------|
| 全部通过 | blackbox.md 状态 → `已执行（通过）`；state.md 环节 11 done；进环节 12（ac-deploy） |
| 有失败 | 问题逐条登记（B# 编号/现象/复现步骤），状态置 `失败`，转入修复循环（§4） |
| 环境不具备 | 与用户协商缩小范围或豁免部分用例，状态置 `豁免` + 理由记录 |

## 4. 问题修复循环（主控驱动）

1. 问题编号（B1、B2…）登记进 blackbox.md 结果节 + `docs/ac/test-results/` 反馈清单。
2. 修复派发：
   - 问题可定位到任务 → `followup_task(dev_t<n>, ...)`（优先，附问题描述+复现步骤+相关 design.md 节+"修复后说明根因与修法"）
   - 无法定位 → 主控评估指派新修复子
3. 修复 settlement → 主控验证（可自动化的复现步骤跑一遍）→ **请用户复测该条**（B# 状态更新）。
4. 循环直至用户确认全部通过或豁免。轮次上限 3 轮，超限上报裁决。
5. 每轮更新 blackbox.md 各条状态与 state.md（executions+1）。

## 5. 边界

- 黑盒修复**不受原任务卡限制**：用户测试暴露的问题就是要修的对象（这是需求的一部分），但修复记录追加进 reviews.md（"黑盒轮"节）供追溯。
- 用户反馈含糊（"好像有点卡"）→ 主控先问清复现条件（ask_user_question），不猜着修。
- 黑盒修复涉及核心调用链时 → 回白盒补一轮相关用例（小循环，不必全量重跑）——跳回规则的体现。
