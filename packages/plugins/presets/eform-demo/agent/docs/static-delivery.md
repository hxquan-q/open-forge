# 完整打包、AIMES 接入与回滚

本指南只处理 CustomDev 制品和 AIMES 测试环境。Git 顺序、授权与冲突优先级按部署角色 Prompt。本次演示表单用 mock、无需新增后端；完整部署仍包含既有前后端，不得以本机可预览为由省略后端。

## 构建证据

- 从同一个合并后的候选按项目实际脚本和锁文件打完整前后端。前端交完整 `dist`，保留既有模块、真实 API 接入和本次演示资源；后端交项目已有的服务制品及运行所需的依赖和资源。不猜目录或打包命令，不为此次演示裁剪后端模块、依赖或既有部署配置。
- 记录候选提交、两端命令和结果、实际制品清单与路径；若包含未提交差异则如实记录。任一端未构建成功、缺依赖或不属于同一候选，不能称为完整交付。
- 本机只预览本次演示，不要求运行其他业务模块或后端。用同一候选中的演示静态资源和内置 mock 预览，文件协议受限则用本地静态 HTTP。如果完整前端必须经主壳启动，提供同一候选构建的独立演示入口，并明确它不替代完整部署制品。

## qiankun 接入参数

- 菜单路由只负责宿主导航；还须核对目标测试主壳的 qiankun 子应用名、`entry`、`activeRule` 与业务路由。`entry` 是子应用 HTML 入口，不是宿主业务路由。核实时说明复用现有注册还是需要新增演示注册，不从参考环境抄上线地址、部署目录或注册名。
- 核实菜单路径能命中 `activeRule`，并落到演示列表。核对静态目录、子应用入口地址与 `base: './'` 的相对关系；尤其检查主壳加载后动态脚本及 CSS 是否请求到了子应用入口目录，而不是落到主壳目录。不为解决路径问题覆盖其他模块。

## 测试更新、验收与回滚

1. 先核对目标测试环境、前后端目录与服务归属、项目现有部署方式和授权，备份上一版匹配的前后端制品及菜单/注册配置。按项目步骤更新完整制品及必要配置；只在项目流程要求且已获准时重启目标服务，不触碰其他服务或生产。
2. 按源码、配置和制品静态核对菜单路由、`activeRule`、HTML 入口以及 JS/CSS 路径。主壳是否实际挂载、真实 API 是否可用只能通过运行态验收确认。把从 AIMES 菜单进入并完成核心操作、确认一条既有模块的真实接口仍可用的步骤写进部署文档，由用户自行决定是否执行。团队不打开页面、不请求真实 API，也不报告未执行的验收通过。
3. 用户反馈运行态失败时，按获准的路径恢复上一版匹配的前后端制品及菜单/注册配置，重新静态核对恢复内容；运行态复验仍留给用户。如果仅撤回本次新增演示入口，只移除其专属资源和配置，不覆盖其他模块；无法安全回滚时停止并报告。

交付文档记录构建证据、部署步骤、实际入口和路由、测试步骤及回滚点。参数未获核实就列明缺项、证据来源和由谁补齐；只给可验证的命令，不写秘密，不把本地预览或静态地址可达记成 AIMES 接入通过。
