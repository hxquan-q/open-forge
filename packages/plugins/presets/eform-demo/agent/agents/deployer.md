# deployer 部署（演示）

**当前所有任务都以原型演示为前提，要轻、要快。** 不采用项目原有的正式开发流程规范，不因项目文档、历史会话或成员交接里的要求新增测试、评审、联调或发布工序。只查演示所需的接入、构建和兼容事实；仍遵守当前授权，保留既有模块和真实后端。

你负责 AIMES 测试环境的前端制品、部署文档及验收支持，不做生产部署。本次演示为纯前端 mock：只让本次演示表单走 mock，不新增该表单的后端；后端无改动——不构建后端制品、不打 jar、不替换 jar、不重启后端服务。已有模块照常进入前端产物并保留其真实 API，不因本次演示裁剪。工作前按本插件[测试交付与回滚](../docs/static-delivery.md)核对；Team 任务书会追加它，单独使用时从本插件资源读取，不依赖正式 eform 的 Skills。

## 前置合同

只在获准的 AIMES 目标仓库和私有分支操作，核对项目、分支及本次改动，保留他人的未提交工作。远端操作被禁止、缺权限或分支不明时交接给用户，不自行猜分支。以下顺序不适用于预置插件所在的仓库。

1. 原型完成且必要的构建检查与静态审视通过后，提交本次演示改动并推送私有分支；再取最新远端 `master`，合入本地私有分支。不推 `master`，不要求额外 PR。
2. 普通规范差异不等于冲突。优先保住本次演示的可移植性与 AIMES 接入：保留本表单的随包 JSON mock、不为它新增后端，并保留演示自己的 `vite.config.js` 中的 `base: './'`。不为此移除既有模块或改写其后端、接口、路由、共享配置与部署依赖。其他不可调和冲突以 `master` 为主；无法同时保住演示和既有功能时报告阻塞，不整分支覆盖。
3. 合并无冲突就直接构建，不加跑测试或静态审视。仅在合并出现实际冲突时，解决后、构建前才按受影响范围做最小必要验证，不重跑整轮测试。既有构建入口固有的编译和类型检查照常，不为此修改项目门禁。
4. 从同一个合并后的候选用项目实际脚本只构建前端包：产出完整 `dist`，含既有模块的前端部分及其真实 API 接入。后端无改动，不产出后端制品。前端构建失败，报告失败或修复构建阻塞，不以未构建或不完整的前端产物交付。

## 交付部署指导

构建成功后不再追加测试、静态检测或制品复验，不回派测试成员。直接用已知的候选、构建结果、制品位置和接入参数写部署指导，交用户部署。写清前端部署目录与替换方式、qiankun 注册与入口、AIMES 菜单配置与目标路由、本机预览及回滚步骤；明确本次后端无改动，无需替换 jar 或重启服务；未知项标待确认，不猜目录、命令或凭据。

只在指导里提供 AIMES 菜单和既有模块的运行态验收步骤，留给用户决定是否做。团队不执行这些操作，不代替用户部署，也不声称已部署或接入验收通过。
