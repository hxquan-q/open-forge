# 电子签字段实现

AIMES CustomDev 实现 Skill。进入前同时确认：

1. 最终需求字段清单或需求结束汇报包含 `signature` 类型字段；
2. 本次用户需求明确要求新增/修改电子签功能。

仅有 signature 字段、仅讨论电子签但缺字段规格、仅纸面签字栏、仅 creator/modifier 归属或操作历史需求均不触发。已提出加签但规格缺失时先由需求角色按 [字段规格](../form-field-specification-and-base-data/SKILL.md) 补确认，再检查双条件，不绕过需求阶段。

## 实现前确认

- 区分手写签名图像、业务确认动作、外部电子签服务和有法律/合规要求的签署。手写签名确认不等于真实身份认证、合规电子签或不可抵赖证据。
- 签署主体、可信身份校验来源、代理/代签、意图确认和失败/重试策略。
- 与记录、字段、内容版本的绑定，签后内容修改是否导致失效。
- 签名状态、撤销/重签、审批/提交后锁定与并发签署。
- 数据/证据/操作者/时间、访问和保留需求；敏感数据不进入普通日志或非授权材料。
- 当前项目已有组件、API、身份上下文、存储和服务端校验能力；未经核实的能力保持待验证，不能从 UserContextHolder 存在推导签名认证已完整。

## 实施和验证

1. 阅读真实字段模型、渲染/编辑、保存/读取、认证授权与测试；优先复用扩展点。
2. 按确认范围设计交互和数据合同，表达签署、失败、撤销/重签、锁定与内容绑定。
3. 在既有架构内接入前端、读写和必要的服务端约束；身份校验、有效性和签后不可改不能仅靠前端。
4. 行为测试覆盖新增/编辑、签署结果、权限/锁定、失败/重试、内容变更与并发风险；演示页面不能代替真实保存和服务端约束。
5. 交付区分已实现、已核实项目能力、待确认与未实现项，不自行引入服务、证书、密钥、身份字段或法律效力承诺；缺能力先报告并确认方案。

## 职责边界

电子签证据不自动等于操作审计；仅用户明确要求新增/修改审计时另用 [操作审计](../operation-audit-domain/SKILL.md)。归属字段按 [用户元数据](../user-metadata-and-audit-boundary/SKILL.md)，不在此重定义。

旧 `esign-craft` 的演示身份、canvas/dataURL、空/待签/锁定状态、CSS/HTML 注入均非 CustomDev 合同；只保留签名关联、意图、状态、失败、重签、锁定这些需要确认的领域问题。
