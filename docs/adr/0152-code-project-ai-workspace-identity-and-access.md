# ADR-0152：Code 项目 AI 工作区身份与双根文件访问

## 状态

已采纳（2026-11-05，实施 TASK-0449；依据用户已确认的 REQ-0031）。

## 背景

Code 项目的需求记录、用户项目说明、Memory / Journal 与 Agent 辅助产物当前部分写入项目 cwd。项目册登记不能作为 Code 能力范围：历史未归册 Code 会话也需访问项目工作区；普通册和 Allstar 册可各自登记同一路径。Runtime 文件工具已有本机和 SSH 两套路径适配，不能把全局 Vetta 数据目录或所有项目工作区授权给当前 Agent。

## 决策

1. **项目身份取规范化位置，不取显示名、basename 或 Allstar 条目 ID。** 本地项目按 Desktop 项目路径合同规范化；SSH 项目按 host identity 与远端 POSIX path 组合。对身份材料计算稳定目录键，目录键不暴露原路径。显示名变化不变；路径变化产生新工作区，不自动扫描、移动或关联旧资料。同一路径在普通册和 Allstar 册重复登记时共享 Code 工作区，登记关系本身仍独立。
2. **工作区独立置于 Vetta 用户数据目录。** 使用 Code 专属目录布局，不放在项目仓库内，也不将全局 workspace 根传给 Agent。Runtime 显式传递当前项目根与当前项目 AI 工作区根；不允许模型根据项目名猜目录。
3. **文件访问是会话级双根授权。** 本机 Code 工具可在当前项目根及其当前 AI 工作区根内读写；SSH 项目的源码与命令继续走远端 SSH 通道，本机 AI 工作区通过独立的本机文件访问路由。根外路径、另一项目工作区及 Vetta 任意用户数据不得因新增根而放行。路径检查同时遵守本地/远端各自大小写和符号链接/规范化合同。
4. **Code 辅助材料默认写 AI 工作区。** Prompt 明示两根各自用途和交付文件迁入规则；项目持久化信息存于 AI 工作区，由 Code 在相关任务按需读取，内容是不可信参考材料。Memory rollover 的 Memory / Journal 路径映射至同项目 AI 工作区，Team 主控与成员以项目 cwd 解析同一映射。
5. **首次迁移逐文件、幂等且不覆盖。** 首次启用分别检查 cwd 下 `MEMORY.md`、`JOURNAL.md`。目标不存在时复制到同目录临时文件并以 no-clobber 提交；完整目标可用后才尝试删除对应源。复制失败、源删除失败、目标已存在均不阻断新工作区使用；目标已存在时不覆盖且保留源。两个文件各自处理。旧 `.vetta/allstar/project-config.md` 不自动迁移。
6. **生命周期按项目位置处理。** 归档、取消归档和从项目册移除不删除 AI 工作区；硬删除项目时沿项目数据删除流程清理映射对应的 AI 工作区。不会因为路径变化或登记状态变化自动删除旧目录。

## 备选方案

- 按 basename 或名称命名：否决，同名路径冲突、改名丢失身份。
- 仅按 Allstar project entry ID：否决，未登记历史 Code 项目无 ID，同路径双册登记无法共享工作区。
- 把 workspace 放进 `<project>/.vetta`：否决，会继续污染项目仓库且把项目资源与 AI 私有辅助数据混为一类。
- 把整个全局 workspace/Vetta Home 加入 fs allowlist：否决，直接访问其他项目和用户数据，违背最小权限。
- SSH Agent 继续只拥有远端 FS：否决，无法使用题设要求的本机持久 AI 工作区；本机根需单独路由，不可伪装成远端路径。

## 后果

- Runtime 装配、工具路径策略、本机/SSH 文件访问、Allstar 配置 UI、Memory rollover、项目删除链路都必须共享同一项目位置 resolver。
- 文件授权需要直接测试允许的两个根与拒绝的外部根，不能只断言 Prompt 文本。
- project-config 的旧 Markdown 文件不会被读取或迁移；用户需在新配置入口重建需要的说明。
- 首次迁移可能按文件部分完成；每个文件可独立重试，旧副本仅在该文件目标成功后删除。

## 回滚

回滚代码后新工作区继续留在 Vetta 用户数据目录，不自动清理；旧项目内 Memory / Journal 副本按迁移时的逐文件结果保留或缺席。旧 project-config 文件从未自动修改。
